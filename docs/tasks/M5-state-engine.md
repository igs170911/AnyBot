## A 段：任務狀態引擎（`spec/10-behavior/1-followup.md`）

1. **事件算出狀態**（`task-events` S1–S6）：
   - 事件的種類照 S2。
   - 每件任務有自己的事件編號；用事件 ID 去重；編號跳號要回錯誤；不認得的事件種類保留但略過。
   - 狀態由純函式從事件算出。計算時不准讀時鐘：時間是事件帶進來的資料。
   - 快照記下「算到第幾筆」和格式版本，版本不符就從零算。
   - 測試：`T-task-events-1`–`6`。
2. **8 種主狀態和細項**（`task-state` S1–S7）：
   - 完成由系統自動驗收，**不需要使用者做任何事**；使用者按 👍 只是把細項升級成「你已確認」，可有可無。
   - 「未驗收」只是誠實的標記，不推播、不要使用者做事。細項：驗收沒通過、有沒驗到的動作、你拒絕了它要做的那一步、沒有看得到的結果。
   - 已取消、已停止各是自己的主狀態，不算失敗，也不算進任務數字。
   - 細項只往前走。
   - 舊版 12 種狀態的對照表照 S6。
   - 測試：`T-task-state-6`、`7`、`8`。
3. **完成閘門**（`task-done-gate` S1–S5）：
   - 四條都成立才完成，全部由系統自動判斷。
   - 做完的標準可以來自使用者、Bot 開始時自己寫的，或程式從做過的動作自動得到的。只有對話的，回覆了就算完成。
   - Bot 可以把標準改得更嚴，不用問。想放寬時不生效、不打斷使用者，提議放進交付報告的「需要你決定的事」，使用者同意才改。每次修改、每個提議都是一筆事件。
   - 使用者要越少介入越好：除了「結果不知道的對外動作」，任何情況都不准為了完成而等使用者。
   - 測試：`T-task-done-gate-1`–`6`。
4. **預算**（`task-budget` S1–S5）：
   - 用量從事件累計，換模型、中斷都不歸零。
   - 超過任何一項，就不再開新的一步，任務＝卡住，細項寫是哪一項。
   - 調高上限後可以接著做。
   - 同一步重試超過上限，就算這一步失敗。
   - 測試：`T-task-budget-1`–`5`。
5. **對外動作的等級**（`task-effects` S1–S3）：
   - 三個等級：唯讀、可重複、不可逆。新工具預設不可逆。
   - 中斷後結果不知道時：唯讀的重做、可重複的先對帳、不可逆的等你按繼續。
   - 測試：`T-task-effects-1`–`4`。
6. **其他任務邏輯**：
   - `T-task-object-3`：紀錄只增不減、編號連續、件數正確。
   - `T-task-entry-4`：每一輪剛好屬於一件；叫醒不開新任務。
   - `T-task-stall-4`：卡住的判斷。
   - `T-goal-brake-9`：「同一件事」的比對規則。
   - `T-goal-followup-13`：`done_when` 的正規表示式和一般字串比對。
7. **協定跟著改**：
   - `crates/protocol` 的 `TaskStatus` 改成 8 種主狀態。`CompletedDetail` 照 `task-state` S2 重新整理細項：哪個主狀態底下有哪些細項。
   - 重新產生 AsyncAPI 和 TypeScript 客戶端。
   - 協定 v1 還沒發佈（`09` K84，發佈日到第一次發佈才定），所以直接改，不用保留舊的。
   - 任務事件的型別放在哪個套件，照 `spec/07` 的依賴方向決定，寫進回報。這次不接伺服器，也不接同步。

## B 段：信任層和同步的純邏輯

8. **把關的引擎**（`spec/10-behavior/2-trust.md`）：
   - 給一個動作和一組設定，算出結果：直接做、先問、拒絕。同時記下第幾關、哪一層、哪條規則、判斷來源（`safety-gates` S1、S2、S4）。
   - 這次只做純邏輯能決定的關卡：
     - 內建底線：`trust-floor` S1 第 1–4 條。
     - 管理員鎖定值的解析：`safety-lock` S1、S3。
     - 使用者的一律允許、這段對話都允許、一律詢問樣式：`safety-always`。
     - 預設規則的六類：`safety-n5` S2。
     - 一律放行、直接操作的開關。
   - 要用到電腦、卡片、hooks 程式、模型審核的部分，在引擎裡留介面，交給 M7 接。
   - 測試：`T-safety-gates-1`、`T-trust-floor-4`、`T-safety-lock-1`、`T-safety-always-3`、`T-safety-always-10`、`T-safety-n5-1`。
   - `T-safety-always-10` 在這次的意思是：一律允許清單只有「使用者按的」那種事件能加；網頁內容、頻道訊息、Bot 回覆裡的字都加不進去。
9. **宣稱等級**（`claim-levels` S1–S5）：
   - 四個等級由程式從證據算出。
   - 只連到「未經把關」證據的最高到「有來源支持」。
   - 重複說、多個模型附和都不升級。
   - 測試：`T-claim-levels-1`–`5`。
10. **同步的合併規則**（`spec/10-behavior/5-devices-account.md`）：
    - `T-sync-id-1`：多台裝置、時鐘有偏差、離線，產生的編號不重複。先看 `foundation` 現有的編號產生方式夠不夠。
    - `T-sync-outbox-4`：重送間隔 1、2、4、8、16、30、30… 秒，不放棄。
    - `T-sync-after-2`：伺服器送出的變化被隨機丟掉、重複、打亂後，本機副本最後要跟伺服器一模一樣。
    - `T-sync-settings-4`：設定以欄位為單位，校正後時間最晚的贏，清單裡每一項各自成立。
    - 這次只做合併和重送的純邏輯，不接資料庫、不接網路。

## 寫法

- 性質測試用 proptest（`spec/06`）。案例數照規格寫的，例如 1,000 組、5,000 組。
- 純邏輯不准讀時鐘、不准自己產生亂數：時間和亂數都從外面傳進來。性質測試裡的亂數由 proptest 產生。
- 規格沒寫清楚的，不要猜，寫進回報的「要問的問題」。不得不先做時，選最小、之後好改的做法，也寫進回報。
- 這次不做（之後的里程碑做）：
  - 需要工具清單的：`T-task-journal-1`、`T-safety-n8-5`（M7）。
  - 需要伺服器的：`T-sync-seq-1`、`T-task-wake-4`、`T-task-sync-3`（M6）。
  - 需要執行端的：`T-task-resume-7`、`T-task-journal-4`、`T-trust-pipeline-8`（M7）。
  - 還沒照 `09` 重寫的：`T-goal-judge-6`（K102）。
  - 遷移用的：`T-task-proof-4`、`T-task-export-3`。
