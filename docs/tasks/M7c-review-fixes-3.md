# M7c 審核修正（第 3 輪，換 grok 接手）

M7c 是「一個動作從頭到尾」：電腦介面、測試用的假電腦端、信任層的單一入口（把關 → 做 → 留證據 → 驗收）、三個工具（讀檔、改檔、跑指令）。分支 `ws/m7c`，工作區 `~/Documents/AnyBotNext-wt/m7c`。前一位做了三輪，這一輪換你。

**已經站住、不要動的**（第三次安全複查確認過）：

- 電腦的每一個操作只收一張單據（`OpTicket`），單據寫死了完整的操作，只有 `trust` 建得出來，不能複製、不能序列化回來、不會出現在任何回傳值裡，用掉就沒了。
- 「要問」的單子欄位不公開、不能複製、綁著發單時的電腦（名稱和宣告的能力），回答一次就用掉，只有結果是「要問」時才會發。
- 這些繞法都擋住了：`sudo nohup mkfs.ext4 /dev/sda1`、`sudo env reboot`、`sudo FOO=1 shutdown -h now`、`sh -c 'reboot'`、`$(reboot)`、`if true; then reboot; fi`、`/sbin/reboot`、`'reboot'` 被拒絕；`cd repo && sudo nohup git push`、`git --git-dir=.git push`、`git -P push`、`rm a.txt; sudo rm -r /opt/app`、`cd /tmp && rm -rf build`、`eval reboot` 會問。

先讀：`AGENTS.md`；`docs/tasks/M7c-one-action.md`（原本的任務）；`docs/tasks/M7c-review-fixes.md`、`M7c-review-fixes-2.md`（前兩輪）；`spec/09` K119 ③ ⑩；`spec/10-behavior/2-trust.md` 的 `trust-pipeline`、`trust-floor`、`sandbox-deny`、`sandbox-levels`、`safety-n5`、`activity-evidence`。然後 `git merge dev`。

行號是 `ws/m7c` 現在的位置，動手前再對一次，清單寫錯的照實回報。

## 一、指令的判讀改成「只認得一小套，其他一律要問」（阻擋項）

前三輪一直在補「看不穿的寫法」，每次補了又冒出新的。這一輪換做法：

1. **認得的寫法只有這些**：
   - 簡單指令：指令名、參數；參數裡的引號（單引號、雙引號）照 shell 的規則拿掉。
   - 用 `;`、`&&`、`||`、`|`、`&`、換行接起來的多段。
   - 開頭的 `名稱=值`（環境變數）。
   - 已知的外包裝：`sudo`、`doas`、`env`、`nohup`、`nice`、`timeout`、`stdbuf`、`time`、`command`、`exec`、`xargs`。**每一個包裝有自己的選項表**：哪些選項帶值、哪些不帶、什麼時候換成真正的指令（例如 `timeout` 的第一個非選項是時間，再下一個才是指令；`env -i` 不帶值；`command -p` 不帶值）。照各自的 man page 寫，查清楚。包裝可以疊好幾層，反覆拿掉。
   - `cd 路徑`（追蹤後面相對路徑的位置）。
2. **其他任何寫法，一律「要問」**，不管在哪台電腦：括號 `( )`、大括號 `{ }`、`!`、反斜線開頭的指令名（`\reboot`）、反引號、`$(`、`${`、`<(`、`>(`、here-doc、`eval`、`source`、`.`、任何 shell 加 `-c`（`sh`、`bash`、`zsh`、`dash`、`fish`… 含 `-lc` 這種合併的選項）、管線的下一段是 shell（`… | sh`）、`alias`、`git -c alias.*`、不帶參數的 `cd`、`cd -`、`pushd`/`popd`、看不出第一個字是什麼的。
3. **這個「看不懂就要問」屬於底線**：任何放寬的設定（一律允許、這段對話都允許、直接做的模式）都不能把它變成直接做。一律拒絕的那幾種（`sandbox-deny`）照舊是拒絕。
4. 一律拒絕的比對不要用字首：`rm -fr /`、`rm -r -f /` 跟 `rm -rf /` 一樣。照解析後的指令名和參數判斷。

測試：上面每一種寫法各一個（描述性的名字），在 Bot 的電腦上、而且開著「直接做」的設定時，結果都是「要問」（或一律拒絕的那幾種是「拒絕」）。用性質測試產生各種組合（包裝疊幾層、選項帶不帶值、前後有無害的指令），驗：只要裡面有一律拒絕的指令，就是拒絕；只要有看不懂的寫法，就不會是直接做。證明會失敗。

## 二、把關判斷的路徑，就是電腦實際用的路徑（阻擋項）

路徑的值（`action.rs`）欄位公開、`resolved` 的建構方式也公開。把關和核准卡用的是「解析過的路徑」，單據交給電腦的卻是「原本的路徑」，`trust` 也沒有再解析一次操作自己的路徑。例子：原本的路徑是 `/Users/me/.zshrc`、解析過的寫成 `/workspace/notes.md`，Bot 的電腦直接放行，你的 Mac 上卡片寫 `notes.md`，實際被寫的是 `.zshrc`。

1. 路徑的值不公開建構，只有 `trust` 建得出來。
2. **解析交給電腦**：把關之前，`trust` 用單據問電腦「這個路徑實際是哪裡」（連結全部解開），把關、卡片、單據都用這個結果。檔案工具（讀、寫、改）也一樣，所以工作資料夾裡指向外面的連結，不會讓寫入跑出去。
3. 電腦執行時，如果那個路徑解析出來跟單據上的不一樣（中間被換掉了），拒絕。

測試：上面那個例子；工作資料夾裡有一個指向外面的連結，寫它 → 照「外面」判斷；把關和執行之間連結被換掉 → 拒絕。證明會失敗。

## 三、「屬不屬於要先問的六類」由把關層自己算（阻擋項）

`gate_full.rs` 的 `six_class` 還是呼叫者傳進來的旗標，沒有人算，預設是 false。開著「直接做」的時候，使用者那一層會在預設規則之前放行，所以 Bot 的電腦上的 `git push`、工作資料夾外面的刪除、你的 Mac 上工作資料夾外面的寫入，都不問就做了。

- 拿掉這個旗標。`trust` 從動作本身算出它屬於六類的哪幾類（指令照第一節的判讀；寫檔、刪除照第二節解析過的路徑）。
- 六類（寄給別人、分享、發佈、付款、刪除、寫到工作資料夾外面…照 `safety-n5`）在「直接做」的模式下照樣要問。
- 測試：開著「直接做」，上面三個例子都是「要問」。證明會失敗。

## 四、兩個小的

1. **單據可以透過電腦介面留下來**：任何套件都能實作電腦介面，單據的檢查只比對電腦名稱和操作種類。一個用真電腦的名字、卻宣告成 Bot 的電腦、工作資料夾是 `/` 的包裝，可以拿到照 Bot 規則發的單據。把發單時電腦宣告的能力和工作資料夾也寫進單據，執行時對不上就拒絕。`crates/computers/README.md` 說單據「不能存下來」，改成照實寫。
2. **編不過的測試**：`engine_input`、`build_evidence`、`finish_run` 用的是從來沒有匯出的路徑，就算那個東西改成公開也照樣編不過。改用真正的模組路徑，並照之前的做法證明「把那條規則拿掉就會編過」。`build_ask_ticket` 要證明單子建不出來，不只是一個欄位不公開。

其他審查提到的（證據的欄位公開、`git --config-env`…）這一輪不做，寫在回報裡。
