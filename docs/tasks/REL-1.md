# REL-1：發佈流程的骨架

`spec/09` K110、K111 定了分支和發佈的流程。CI-1 做完了第一步：每次推上去在 Linux 跑 `make check`。這次做剩下的：

- 推 `dev` 時，Windows、macOS 也編譯、跑基本測試；全綠後自動出**開發版**。
- 在 `main` 上打版本標籤時，編三種系統的安裝檔和伺服器映像，建 **Release 草稿**。
- 每週排程的安全檢查。
- `docs/wiki/` 有改動時，自動發佈到 GitHub wiki。

**先不簽章**（K110 ③）：這次不碰任何憑證，也不用任何自己設的金鑰。

你在並行工作（`AGENTS.md` 第七節）：自己的工作區和分支，從 `dev` 切，分支名用 `ws/rel-1`。

**你是一次性執行的**：回合一結束，背景工作就會被收掉。要跑很久的指令用前景跑、timeout 設長，不准結束回合去等通知。

先讀：
- `AGENTS.md`。
- `spec/09` K110、K111、K68（先不支援的平台）；`spec/06` 的「CI 和發佈」那一列；`spec/07` 的 `.github/workflows/`。
- `spec/10-behavior/5-devices-account.md` 的 `install-n10`（版本字串）、`install-n24`（發行包）。`install-n9`（簽章）這次不做。
- `.github/workflows/ci.yml`、`Makefile`、`docs/testing.md`、`tools/iron-laws/src/workflows.rs`。
- `apps/desktop/`、`apps/server/`、`apps/cli/`、`apps/runner-service/`：現在各自能編出什麼。

## 現況（先確認，跟你看到的不一樣就寫進回報）

- 桌面 App 還是空殼，但編得出來。伺服器、命令列、背景服務各有一個執行檔。
- repo 裡還沒有 Dockerfile。
- 版本號在 `Cargo.toml` 的 workspace 和 `apps/desktop/src-tauri/tauri.conf.json`，現在都是 `0.1.0`。
- `main` 有保護規則：只收 `check` 這個檢查全綠的 commit。工作流程**不准**往 `main`、`dev` 推任何 commit。

## 1. 推 `dev` 時：三種系統都驗（K111 ②）

1. Linux 照舊跑 `make check`（工作名稱 `check` 不准改，`main` 的保護規則認這個名字）。
2. 新增 Windows、macOS 的工作：
   - 編譯整個 workspace（`--locked`）。
   - 跑**基本測試**：不需要 PostgreSQL、不需要瀏覽器的那些。用 Makefile 的目標跑，不要在工作流程裡另外抄一份指令；需要新目標就加在 Makefile。
   - 這兩個工作只在推 `dev`、`main` 時跑。工作分支和 PR 只跑 Linux 的 `check`（省時間）。
   - 第一次在 Windows、macOS 的 runner 上跑，預期會有要修的地方。**不准為了過關改產品行為、跳過測試、放寬檢查**；真的是平台差異的，在 Makefile 或測試工具裡處理，並寫進回報。
3. runner 的系統版本寫死（例如 `windows-2025`、`macos-15`），不用 `latest`。

## 2. 開發版：`dev` 全綠後自動產出（K111 ②）

1. 三種系統的工作都綠了之後，才開始包安裝檔：
   - 桌面 App 的安裝檔：`install-n24` S1 列的平台，能做幾個做幾個。Mac（arm64、x86_64）、Windows（x64）、Linux（x86_64 的 .deb、.rpm、壓縮檔）是這次一定要有的；Windows arm64、Linux aarch64 做得到就做，做不到寫進回報。
   - 伺服器映像：`linux/amd64`、`linux/arm64`。
2. **開發版跟正式版並存**：
   - App 名稱是「AnyBot Dev」，系統認的識別名稱不一樣，資料夾也不一樣：同一台電腦可以同時裝開發版和正式版，互相看不到對方的資料。
   - 這是編譯時決定的「發佈管道」（開發版、正式版），不是執行時的旗標或環境變數。管道的名稱和它對應的資料夾名稱，放在一個地方定義，App、命令列、背景服務都從那裡拿。
   - 附測試：兩個管道算出來的資料夾不一樣；正式版的資料夾名稱跟現在的一樣（不准因為這次改動而變）。
3. **版本字串**照 `install-n10` S1：「v<版本>-<commit> · 建置時間」。
   - 現在已經有的就沿用；沒有的補上。CI 上編的不會有 `-dirty`。
   - 建置時間從外面傳進編譯（CI 給的時間），不要讓同一個 commit 每次編出來的內容無故不同：除了這一個時間以外，其他都固定。
4. **固定的 dev 預先發佈頁**：
   - 一個固定的標籤（例如 `dev-build`，不准是 `v` 開頭），每次 `dev` 全綠就移到新的 commit；對應一個標成「預先發佈」的 Release，安裝檔換成新的，舊的拿掉。
   - 說明裡寫：對應哪個 commit、什麼時候編的、這是開發版、**沒有簽章時各系統會跳什麼警告、怎麼放行**（Mac、Windows 各寫清楚；Linux 寫怎麼驗 SHA-256）。
   - 附一個 `SHA256SUMS` 檔，列出每個安裝檔的雜湊。
5. **伺服器映像**推到 `ghcr.io`，標 `dev` 和那個 commit 的短雜湊。
   - Dockerfile 用多階段：編譯的階段和執行的階段分開；執行的階段不放編譯工具、不用 root 跑。
   - 基底映像釘在摘要（`@sha256:…`），旁邊註解寫版本。
   - 映像裡的伺服器照 `spec` 的規定啟動：設定只從啟動檔來（`--bootstrap`），**不准加環境變數當設定**。
   - 驗證：在 runner 上把映像跑起來，執行 `--version`，輸出的版本字串要對。
   - **你的開發機上不准跑 Docker**（`AGENTS.md` 第一節）。Dockerfile 只在 GitHub 的 runner 上驗。

## 3. 正式版：在 `main` 上打版本標籤（K110 ②、K111 ④）

1. 觸發：推 `v*` 的標籤。
2. 先檢查，不過就整個停下、什麼都不發佈：
   - 標籤指到的 commit 在 `main` 上。
   - 標籤跟版本號一致：`v0.1.0` 對 `0.1.0`。`Cargo.toml` 和 `tauri.conf.json` 的版本號也要彼此一致（這一項同時加進 `make check`，平常就擋）。
   - 那個 commit 的 `check` 是綠的。
3. 編的東西跟開發版一樣，但管道是正式版；安裝檔、`SHA256SUMS`、伺服器映像（標版本號）。
4. 建 **Release 草稿**，不直接公開。`-rc.N` 這類標籤標成「預先發佈」。說明同樣要寫沒有簽章時怎麼放行。
5. 映像的 `latest` 標籤：只有正式版（不是 `-rc`）的 Release **公開之後**才移過去。
6. **預演**：要能在不打標籤、不發佈的情況下把整條流程跑一遍。
   - 推 `ws/rel-` 開頭的分支時，發佈的工作流程用「預演」模式跑：照樣檢查、編譯、打包、算雜湊，產物放在那次執行的附件裡；**不建 Release、不推映像、不動任何標籤**。
   - 監督者就是用這個方式驗你的成果。

## 4. 每週的安全檢查（K111 ⑤）

- 每週排程跑一次，也可以手動觸發。
- 查相依套件的新安全公告（Rust 和前端的都要）、掃整個 git 歷史有沒有金鑰。
- 有問題就讓這次執行失敗（GitHub 會通知）。不自動開 issue、不自動改檔。

## 5. wiki 自動發佈

- `main` 上 `docs/wiki/` 有改動時，把那個資料夾的內容發佈到這個 repo 的 wiki（wiki 是另一個 git repo，分支是 `master`）。
- 只給這個工作需要的權限。內容沒變就不產生新的 commit。
- wiki 上有、但 `docs/wiki/` 沒有的頁面：刪掉（以 `docs/wiki/` 為準）。

## 6. 安全規則（K110 ④，公開 repo）

1. 照 CI-1 的規則：最上面的 `permissions` 只給 `contents: read`；每個工作有 `timeout-minutes`；`uses:` 釘在完整的 commit 雜湊；下載的工具固定版本並驗 sha256。
2. 這次有些工作需要寫入的權限（建 Release、推映像、推 wiki）：
   - 寫入的權限只寫在**需要它的那一個工作**上，其他工作照舊唯讀。
   - 需要寫入權限的工作，不准跑來自 PR 的程式碼；外面的人的 PR 拿不到任何寫入權限（K111 ⑤）。
   - 只用 GitHub 自動給的 `GITHUB_TOKEN`，不用任何自己設的金鑰。
3. iron-laws 的工作流程檢查跟著加強，各附「塞進去會被擋」的測試：
   - 最上面的 `permissions` 出現任何寫入 → 擋。
   - 有寫入權限的工作，觸發條件包含 `pull_request` 或 `pull_request_target` → 擋。
   - `runs-on` 用 `latest` → 擋。
   - 工作流程裡把 `github.event` 的文字（標題、分支名、留言）直接塞進 `run:` 的指令 → 擋（要先放進 `env:` 再用）。
4. 第三方 action 優先用 GitHub 官方的（`actions/*`、`docker/*` 這類官方組織的）。要用別人的，照 `AGENTS.md` 先查維護者和使用量，寫進回報。

## 7. 文件

- `docs/release.md`：怎麼發一個版本（一步一步）、怎麼預演、開發版在哪裡下載、出問題怎麼退回。
- `docs/wiki/` 的「安裝與使用」「分支與發佈」跟著更新：做好的標 ✅，並寫清楚現在下載得到的是空殼的開發版。
- `docs/plan.md` 的 REL-1 那一列標成完成。

## 怎麼驗證

- **你不能 push，也不要用 `gh`。**你在本機能做的：
  - `make check` 全綠。
  - iron-laws 的新檢查和測試。
  - 管道、版本字串、版本號一致的測試。
  - 自己逐行讀過每個工作流程。
- 你回報後，由監督者把 `ws/rel-1` 推上 GitHub 跑預演。失敗的紀錄會放進你工作區的 `target/ci-logs/`，再請你接著修。第一次回報不用保證一次就過，但要把你擔心的地方列出來。
- 真的開發版和正式版，要等合進 `dev`、`main` 之後才會第一次跑。打版本標籤由使用者決定。

## 這次不做

- 簽章、公證、更新檔的簽章（`install-n9`）。
- App 裡的自動更新（`install-n7`、`install-n8`）。
- 伺服器的安裝程式（`install-n12`、`install-n13`）。
- 每個版本的發佈日期表（`spec/09` K84）：等伺服器那邊做了再接上。
- 不改產品行為。發佈管道和版本字串以外的產品程式都不動。
