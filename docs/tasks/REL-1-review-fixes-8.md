# REL-1 審核修正（第 8 輪，小的）

第八次預演**全部通過**：打包六個工作全過；三種系統的檢查全過（Linux 491、macOS 485、Windows 157 個測試，`windows tests ran: 166`）。快速審查確認開發版那條路沒有阻擋項：預演、PR、fork、手動執行都碰不到發佈；兩次開發版發佈不會重疊；頁面不會新舊混雜。`load: true` 加 `outputs` 那個組合是合法的。

剩一個阻擋項，在正式版那條路上，是第 7 輪改出來的。加上三個很小的安全項目。這一輪只做這四項，做完就合。

先做：`git merge dev`。

## 一、正式版的映像沒有版本標籤（阻擋項）

`deploy/release/push-images.sh` 組多架構索引時，這一輪拿掉了版本標籤（`:0.1.0`、`:0.1.0-rc.1`）；註解說「由呼叫的人加」，但 `release.yml` 只移 `:dev`，沒有任何地方加版本標籤。

- 後果：第一次推 `v0.1.0`，建出來的草稿的映像沒有 `:0.1.0`（`docs/release.md` 說有）；Release 公開時，`move-latest.sh` 拿 `:0.1.0` 當來源，不存在，`latest` 那個工作就失敗。
- 自我測試（`release-selftest.sh` 大約第 402 行）斷言這個標籤**不存在**，把這個錯鎖住了。
- 修法：正式版在組索引那一步把版本標籤加回去（開發版照現在，只有 commit 那個標籤，`:dev` 換頁成功之後才移）。自我測試改成驗正式版有版本標籤、開發版沒有；證明會失敗。

## 二、三個小的

1. **每次開發版發佈都留下一個公開的 `dev-build-next-<sha>` 標籤**，失敗時還會留下它的頁面，而下一次只清自己那個 SHA 的。改成：刪舊的 Release 時連標籤一起刪，然後在同一次編輯裡把草稿改名並公開。這樣也一起拿掉了「改名後推標籤失敗」那個空窗。查 GitHub 文件確認 `gh release delete --cleanup-tag` 和 `gh release edit` 的行為。
2. **「還是不是 `dev` 最新」那次再查，排在推映像之後**（`release.yml` 大約 357–380 行），跟註解寫的「任何寫入之前」不一樣。移到發佈工作的第一步。
3. **自我測試**：`docker`、`gh`、`git` 的替身排在 `PATH` 最前面，但環境裡如果設了 `ANYBOT_DOCKER`，腳本還是會用到真的 docker（`move-latest.sh`、`move-dev.sh`、`push-images.sh`）。自我測試一開始就把它清掉，並加一個檢查：設了 `ANYBOT_DOCKER` 指到一個會記錄的假程式，自我測試也不會叫到它。

## 驗證和回報

- `make check` 全綠就 commit；`git merge dev`、`make check`；簡短回報（四項怎麼改的、新的「會失敗」幾條、查到的文件）。
- 其他想到的改進寫在回報裡，不要做。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`（測試裡的替身除外）、不准用 `pkill` 或 `killall`。不准在這台電腦上跑真的 Docker。發佈的條件只准變嚴、不准放寬。遇到「Operation not permitted」是沙箱在擋，不要繞過。
