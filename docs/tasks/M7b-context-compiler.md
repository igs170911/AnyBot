# M7b：上下文編譯器（純函式的那一半）

每次問模型之前，要給它看什麼，由程式重新組一次：這個東西叫上下文編譯器（`spec/09` K95、K107、K114）。它取代舊做法「用到 60% 就叫模型寫摘要」。

這次做**純函式的那一半**：一個新套件 `crates/context`，吃「任務的事件、原始紀錄、記憶、模型的能力」，吐出「給模型的請求、清單、要記下的事件」。它不發任何請求、不碰檔案和資料庫。把它接進真的回合（執行端的回合迴圈）是下一個里程碑，這次不做。

做完後，下面列的 10 個規格編號要有整列驗到的測試，名稱照 `AGENTS.md` 第二節第 4 條。

你在並行工作（`AGENTS.md` 第七節）：自己的工作區和分支，從 `dev` 切，分支名用 `ws/m7b`。

**你是一次性執行的**：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長，不准結束回合去等通知。

先讀：
- `AGENTS.md`。
- `spec/09`：K95、K103、K104、K106、K107（壓縮的順序 ①–③ 那一段）、K114。
- `spec/07`：`context` 套件那一列和依賴表。
- `spec/10-behavior/3-chat-bots.md`：`chat-compact`、`context-build`、`context-must`、`context-mask`、`context-ref`、`context-state`、`context-budget`、`context-manifest`，**整段讀**。
- `spec/10-behavior/6-integrations-models-settings.md`：`models-capabilities`（S3–S8：這一步可以放多少、估算、校正、安全邊際）、`models-handoff`。
- `spec/10-behavior/1-followup.md`：`task-events`、`task-state`、`task-effects`。
- `crates/models`：能力表、token 估算、中立的請求型別。`crates/domain`：任務的事件和狀態引擎。

## 套件

- 新套件 `crates/context`。依賴只能是 `foundation`、`protocol`、`domain`、`models`（`spec/07`）。depcheck 的設定跟著加。
- **純函式**：
  - 沒有 `async`、不建執行環境、不發請求、不讀寫檔案、不碰資料庫、不看時鐘。
  - 只用 `models` 的型別、能力表和 token 估算；不准呼叫閘道送東西。
  - 記憶和原始紀錄由呼叫的人先拿好，當參數傳進來。
- 輸入的型別放在 `context` 自己裡面（對話、步驟、工具要求和結果、找回來的記憶、收起的事件……）。之後執行端會把真的紀錄轉成這些型別，這次不用管紀錄在資料庫裡長什麼樣。任務的事件和狀態用 `domain` 已經有的；缺的事件種類（「收起」）加在 `domain`，照 `task-events` S5 的相容規則。
- `runner` 這次不改。

## 要做的

照規格的每一節做。下面只列容易漏掉的。

1. **組的結果固定**（`context-build` S2、S3、S4）：
   - 同樣的輸入組兩次，請求序列化之後位元組完全一樣。注意雜湊表的順序、浮點數、時間。
   - 內容分三段，會變的放後面。
   - 相鄰兩次的前段要一樣，除非中間有收起的事件、換了模型、快照更新。
2. **一定要放的**（`context-must`）：放不下就回「上下文預算不夠」和缺多少，**不准截斷**。只有你的長訊息可以換成參照（K114 ⑤）。
3. **工具結果的整理和收起**（`context-mask`）：
   - 一行摘要、給模型看的內容（頭、尾、錯誤位置）、編號。
   - 收起是一筆事件；編譯器回傳「這次要記下的事件」，由呼叫的人去記。下一次把它當輸入傳進來。
   - 兩筆收起的事件之間，收起的範圍不變。
4. **狀態摘要**（`context-state`）：從任務的事件算，每一項帶來源的事件編號。
5. **放不下時少放的順序**（`context-budget` S2）和水位（K114 ④）。
6. **清單**（`context-manifest`）：跟請求對得起來；不含秘密。
7. K114 的數字集中放一個地方，每個數字旁邊註明對應 K114 的第幾點。

## 這次要驗到的規格編號（10 個）

都是性質測試和單元測試，直接測 `crates/context`。性質測試每個 1,000 組，用 proptest。被測的要是產品真正在用的那段程式，不是測試裡另外寫一份。

| 編號 | 重點 |
|---|---|
| `T-context-build-1` | 同樣的輸入，兩次的請求位元組一樣 |
| `T-context-build-2` | 長任務每一步組一次：前段只在三種情況下改變 |
| `T-context-must-1` | 只有兩種結果：每一項都在而且一字不差，或者不送出、回「上下文預算不夠」 |
| `T-context-mask-2` | 要求和結果成對、你的話和回答不變、不該收的沒收、兩次收起之間的累積量 |
| `T-context-mask-3` | 5,000 行的輸出：頭、尾、錯誤位置、一行摘要 |
| `T-context-state-1` | 狀態摘要是事件的純函式，每一項對得到事件編號 |
| `T-context-state-4` | 300 個步驟的計畫怎麼縮短 |
| `T-context-budget-1` | 送出的請求不超過可以放的；沒送出的都是「上下文預算不夠」 |
| `T-context-budget-2` | 少放的順序；一定要放的到最後都在；最近 2 步的原文都在 |
| `T-context-manifest-1` | 清單和請求對得起來；估算加總對 |

產生器要涵蓋：
- 很長的你的訊息、很多條限制、很長的標準。
- 各種長度的工具結果、重複的結果、有錯誤位置的結果。
- 還沒確認的對外動作、結果不知道的動作。
- 一步有好幾個工具要求。
- 做到一半換模型（可讀長度變大、變小）、快照更新。
- 可讀長度從很小（2,000）到很大（1,000,000）。
- 中文和英文混合的內容。

其他 `T-context-*`、`T-chat-compact-*`、`T-files-n1-7` 需要真的回合、畫面或工具，這次不驗。但函式庫要把它們需要的功能做出來（例如：重複的結果只放一次、長訊息換成參照、清掉衍生資料後重組結果一樣），並各附至少一個單元測試；測試名稱**不要**用那些規格編號（用了會被當成整列驗完）。

## 這次不做

- 接進執行端的回合迴圈、`read_result` 工具、/context 和 /compact 指令、畫面。
- 記憶的檢索（輸入是「已經找回來的記憶清單」）。
- 模型寫的摘要（K107 ④）。
- 分詞器套件（K112 ⑨）：token 估算用 `models` 現在有的。
