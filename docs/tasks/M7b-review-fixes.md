# M7b 審核修正

M7b 在 GitHub 的 Linux 檢查是綠的（502 個測試全過）。合併之前我請了一個獨立的審查把整個套件讀過，結論是**還不能合**。下面每一項我都對過程式。

做得好的先講：組出來的結果是決定性的（有順序的容器、沒有時鐘和亂數）；沒有照位元組切字、沒有會當掉的寫法；數字跟 K114 一樣；沒有碰 `crates/models`；沒有壓掉檢查；檔案和函式的長度都在限制內。

先做：`git merge dev`。`spec/09` 的 K114 多了 ⑪–⑯ 六條，就是這次審查發現規格沒寫死的地方，先讀。

## 一、規格編號多報了

任務要 10 個編號，你從 `tools/spec-trace/baseline.txt` 拿掉了 24 個。從那份檔拿掉一個編號，意思是「這一列的每一項預期都驗完了」。審查逐個對過，24 個裡只有 `T-context-build-1` 站得住。

1. **這 14 個放回基準檔**，它們的種類是「整合」，預期裡寫的是跑起來的任務、畫面、`read_result`，這個套件沒有執行端，驗不到：
   `T-context-budget-3`、`-4`、`-5`，`T-context-manifest-2`、`-3`，`T-context-mask-1`、`-4`、`-5`，`T-context-must-2`、`-3`、`-4`、`-5`，`T-context-state-2`、`-3`。
   - 對應的測試改成描述性的名字（不帶編號）。真的有驗到東西的留著；下面點名「什麼都沒驗到」的，改到會失敗，或刪掉。
   - 規則再講一次（`AGENTS.md`、K86、K109 ⑪）：測試要帶編號，那一列最後一欄的**每一項**都要驗到，而且要在那一列的種類要求的那一層驗。做不到就用描述性的名字。多報比少報嚴重：它讓「還沒驗」的清單變短，之後沒有人會回頭補。
2. **剩下的 9 個（任務本來要的）目前也都不算數**，見第四節。修到算數之前，先放回基準檔；修好一個、拿掉一個。

## 二、編譯器的三個錯（一定要修）

1. **「剛換過模型」永遠不會變回來**（`collapse.rs` 判斷換模型的那個函式）。事件是 組了上下文(1)、換了模型(2)、組了上下文(3)、組了上下文(4) 時，它一直回「換過」。結果：換過一次模型之後，每一步都把紀錄裡收起的丟掉，結果全部原文放回來、又沒有記事件；放不下的那幾步每次都重記一筆、把全部編號再列一次。照 K114 ⑪：只算到下一筆「組了上下文」為止。
2. **換模型時的重新決定不對**（`plan_collapse`）。現在不管換大換小都把收起的清空，而且已經記過的那些不再重新評估。例子：30 步、每步 1,500 字，第 0–19 筆在可讀長度 32k 的模型上收起了，換成 24k 的：比較小的模型上反而一筆都沒收。照 K114 ⑪：不看之前收了哪些，照新模型從頭算一次，記一筆「這是全部，取代之前的」；之後照事件的先後讀。
3. **70% 的水位沒有作用**（`compile.rs` 的迴圈）。兩個分支都是「放得下就送」。第一項少放完還在 99% 的請求會被送出去，下一步馬上又放不下。照 K114 ④、⑫：放不下才開始少放；開始之後照順序、從最舊的開始，降到 70% 以下才停。

## 三、應該修

1. **順序**（`compile.rs` 組第二段的地方）：現在「目前這一步、還沒回答的問題、還沒確認的動作」排在對話前面；你的話、Bot 的回答、步驟是三份清單接起來，沒有照發生的先後；舊對話排在步驟後面。多一則回答或多一個工具要求，前面的區塊就變了，而這不在 `context-build` S4 准許的三種情況裡。照 K114 ⑯ 改。
2. **輸入裡有四樣沒人讀**（`input.rs`）：還沒回答的問題、秘密、層級、釘選快照的版本。沒有卡片事件的問題不會出現在請求裡；回答過的卡片一直算「還沒回答」（`state.rs`）。每一樣：要嘛用上（照規格哪一條寫清楚），要嘛從輸入拿掉並在回報說明為什麼不需要。
3. **缺多少算錯**：只算了中間那一段的。系統提示 3,000 token、可以放 2,000 的時候，回「預算不夠，缺 0」。照 K114 ⑬。
4. **一樣的內容只放一次，檢查的順序錯了**（`assemble.rs`）：第 1 步和第 16 步讀同一個 700 字的檔、第 1 步被收起時，第 16 步寫「跟第 1 步的結果一樣」，內容在請求裡哪裡都沒有，而第 16 步還在最近 2 步裡。照 K114 ⑭。
5. **超過上限的結果**（`mask.rs`）：最多留 4 個錯誤位置、每個佔上限的三分之一。20,000 字、4 個錯誤位置、上限 8,000 時，給模型看的大約有 16,000 字；「省略了多少」也沒有扣掉這幾段。照 K114 ②、⑮。
6. **舊對話一律砍到最後 10 則，還標成「預算」**，放得下也一樣（400 則短的、可讀長度 16k）。放得下就不該少放。另外第 2、3 項少放沒有記事件（`context-budget` S5、K114 ⑧、⑫）。
7. **轉成請求的那一段沒有測試，而且看起來不對**（`output.rs`）：系統提示又重複成一則 assistant 的訊息；工具要求和結果變成 tool 角色的訊息、沒有呼叫的編號，模型對不起來。清單上寫的是模型的分詞器，估算卻一律用公式。把它改對，並加測試：每個工具要求和它的結果用同一個編號配成對；系統提示只出現一次；清單寫的估算方式就是實際用的那一種。
8. **默默給預設值**：`state.rs`、`domain` 的收起事件解析、`output.rs`、`compile.rs` 各有一處。解析不出來要往上回錯誤，不是當成空的。

## 四、九個測試（每個都要驗到整列）

產生器的共同毛病先修：每筆紀錄的編號都一樣；工具結果只有 ASCII 的 `x`；「中英混合」那個樣式其實是一個固定的字串。要有不同的編號、真的中英混合（含會佔好幾個位元組的字）、長短不一。

| 測試 | 現在的問題 | 要改成 |
|---|---|---|
| `t_context_budget_1` | 預期用的是編譯器自己寫在清單裡的數字；可讀長度只到 500–60,000，那一列寫 4,000–1,000,000 | 測試自己另外估一次送出去的請求（不呼叫編譯器的估算函式）；範圍照那一列；沒送出的每一組都要驗是「上下文預算不夠」 |
| `t_context_budget_2` | 「一定要放的」只驗了限制條件；「最近 2 步的原文」是用產品的排版函式算的，而且把「跟第 N 步一樣」那一行也算成原文 | 一定要放的每一種都驗；原文拿輸入的原始內容直接比 |
| `t_context_build_2` | 斷言永遠不會失敗（那個旗標每一步都是真的）；256 組不是 1,000 組；沒有產生換模型 | 前段位元組一樣，只有三種情況例外，三種都要產生得到；也要有「三種都沒發生」的組，而且那些組前段真的一樣 |
| `t_context_manifest_1` | 「一定要放的有放」驗成「有一個系統區塊」；來源編號沒比 | 清單的每一項對得到請求裡的一段和它的來源編號；加總自己算 |
| `t_context_mask_2` | 最多 9 步、可讀長度 60k 以上，所以從來沒有任何東西被收起；每組只組一次；15% 的規則和短結果沒驗 | 步數和大小要讓收起真的發生；同一組連續組好幾步；驗 15% 的門檻、600 字以下不收、成對、你的話一字不差 |
| `t_context_mask_3` | 錯誤那一行加在最後一行，靠結尾那一段就會過；錯誤位置是第 2,999 個字，不是第 3,000 行；沒驗省略了多少 | 照那一列：錯誤在中間的第 3,000 行；頭、尾、錯誤前後三段都驗；省略的數量要對 |
| `t_context_must_1` | 可讀長度 80k–400k（那一列是 2,000–200,000），所以從來沒有不夠、也沒有換成參照；做完的標準那個迴圈是空的；目前步驟、還沒回答的問題、還沒確認的動作、工具說明都沒驗 | 範圍照那一列；每一種一定要放的都驗「一字不差，或整個沒送出」；兩種結果都要產生得到 |
| `t_context_state_1` | 改過的檔和雜湊沒驗，摘要裡根本沒有 | 照那一列每一項驗；摘要要有那幾項 |
| `t_context_state_4` | 直接把「要縮短」的旗標設成真，沒有經過產品判斷門檻的函式；沒驗做完的步驟不在裡面、目前這一步在 | 從 300 步（280 個做完）的輸入開始，讓產品自己判斷；驗做完的只寫數量 280、沒做完的 20 個全列、目前步驟和還沒解決的問題都完整 |

**每個測試都要證明它會失敗。** 帶編號的 10 個測試，每一個：暫時把它守的那條產品規則改壞（例如把 70% 改成 100%、把 600 改成 0、把配對拆掉），跑這個測試，確認它變紅，再改回來。回報裡列一張表：測試、你改壞了什麼、有沒有變紅。改壞了還是綠的，就表示測試沒驗到，回去修測試。

## 驗證和回報

- 順序：二 → 三 → 四 → 一的收尾（基準檔對齊）。每一大項 `make check` 全綠就 commit，不要累積。
- 回報（簡短）：每一項怎麼改的；第四節「會失敗」的那張表；最後基準檔裡 `T-context-*` 還剩哪幾個；有沒有哪一項你認為不該照做、為什麼。
- 做不完的照實寫。編號寧可少報。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。同一個測試跑到第 3 次還不過就換做法；還是不行就寫進回報、先做別的。這個套件是純函式：沒有 `async`、沒有時鐘、沒有檔案、沒有網路。不要改 `crates/models` 裡的任何檔。同時有別的 agent 在別的工作區做事，編譯和測試會互相等，屬於正常。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`、不准用 `pkill` 或 `killall`。遇到「Operation not permitted」是沙箱在擋，不要繞過。
