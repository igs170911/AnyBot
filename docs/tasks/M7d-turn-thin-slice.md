# M7d：一輪從頭到尾（最薄的一條路）

> 定稿，照 K119 之後的規格寫（`spec/09` K119、`turn-loop`、`task-events` S2、`context-fixed`、`report-delivery`、README 新的幾段）。
> 原本的〔待定〕都定了，見「監督者定了的六點」和「已經定了的」。

這次把執行端的**回合迴圈**做出來，走通第一條從頭到尾的路：

你說一句話 → 開一件任務 → 一輪裡用一次改檔工具、一次指令工具 → 每個動作過信任層（把關 → 做 → 留證據 → 驗收）→ 模型不再要工具 → 收尾 → 完成閘門 → 程式產生交付報告。

**沒有伺服器、沒有畫面。**這一輪在本機發起、在本機跑，紀錄寫進「紀錄」這個介面後面的記憶體實作。這不是假的路：規格要求這台自己發起的那一輪，伺服器連不上也照做（`spec/02` §3.3、`09` K113 ①、`trust-pipeline` S7）。之後接伺服器（M7j）時，回合的程式不用改。

做完後，下面列的 18 個規格編號要有整列驗到的測試，名稱照 `AGENTS.md` 第二節第 4 條。

你在並行工作（`AGENTS.md` 第七節）：自己的工作區和分支，從 `dev` 切，分支名用 `ws/m7d`。開工前 `dev` 要已經有 M7b（`crates/context`）、M7c（信任層的單一入口、假電腦端）、M7a-4（模型閘道）。少一個就停下來回報。

**你是一次性執行的**：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘），不准結束回合去等通知。

## 監督者定了的六點（照每一點「建議」那一行做）

這六點原本規格沒寫，監督者看過，都照建議定了，其中四點已經寫進規格：第 1 點（`task-events` S2 多了「交付報告」這一種；README 寫明在這一層讀報告算驗到，所以 `T-turn-loop-11`、`T-task-done-gate-7` 用編號）、第 2 點（`task-events` S2 的「把關結果」多了「是不是只看」）、第 3 點（`turn-loop` S8）、第 4 點（`models-errors` S1 多了一類「空白的回覆」；`T-chat-n3-6` 這次仍然不驗，等 `models` 合進來）。第 5 點留給 M7g。第 6 點照建議：記成被拒，不准自動允許。

1. **交付報告是哪一種紀錄；在這一層看報告算不算驗到。**
   - `report-delivery` S7 說報告產生時寫成一筆紀錄，但 `task-events` S2 的表沒有這一種。K119 ⑰ 算驗到的觀察點也沒有直接寫「交付報告…」。
   - 建議：加一種任務事件「交付報告」，帶報告的內容；算狀態時略過它。報告既然是這件任務的一筆紀錄，「沒有交付報告」「報告的『要你注意』列出…」就是在讀「這件任務的紀錄」，這一層算驗到。
   - 影響：`T-turn-loop-11`、`T-task-done-gate-7`。監督者說不算的話，這兩個改用描述性的名字，編號是 16 個。
2. **「是不是只看」記在哪一筆。** `task-done-gate` S6 要看「最後一個不是只看的動作」；只用唯讀指令的指令也算只看，這只有信任層算得出來。`task-events` S2 沒有欄位放它。
   - 建議：放在「把關結果」那一筆（M7c 的把關紀錄已經帶著）。狀態引擎只讀這個欄位，不自己認指令。
   - 影響：`T-task-done-gate-7`。
3. **沒有明確的標準時，收尾要不要寫「開始驗收」。** `turn-loop` S8 只講了有標準的情況。
   - 建議：不寫。沒有東西要另外查：狀態引擎直接從動作層的驗收結果和 `task-done-gate` S6 算。任務細項也就不會經過「驗收中」。
4. **模型一直回空白，閘道怎麼告訴執行端。** K117 ③ 說再問一次還是空白就照失敗處理，`models-errors` S1 的表沒有這一類；`turn-loop` S9、S11 要執行端分得出「空白」和別的失敗。
   - 建議：閘道交出自己一類的結果（空白的回覆）。在定下來、`models` 合進來之前，`T-chat-n3-6` 這次不驗。閘道已經分得出來的話，照 `turn-loop` S9、S11 做，用描述性的名字測，寫進回報。
5. **換到備用模型時，閘道怎麼把控制交回執行端。** `turn-loop` S4 要執行端照新模型重組一次再送；閘道要是自己拿同一個請求去問備用模型，就重組不了。
   - 建議：這個留給 M7g，`T-turn-loop-4` 這次不驗。這次的測試都不設備用模型。閘道真的交出換模型紀錄時，照實寫一筆「換了模型」，不要當成沒發生。
6. **入口回「要問」時，這一版怎麼辦。** 卡片是 M7e。
   - 建議：記成「被拒（這一版還不能問）」，結果給模型，不執行，同一步後面的照 `turn-loop` S5 記「沒執行：前一個動作被拒絕」。**不准自動允許。**這不算「你拒絕了」，不准動到「你拒絕了它要做的那一步」那個細項。寫進回報的「偏離規格的地方」。

## 要用到 `models`、`context` 的哪些公開的東西

這兩個套件還在別的分支審查。這次**只准用它們公開的型別和函式**，不准改它們，也不准讀別的分支。名字以合進 `dev` 的那一版為準。

**開工第一件事**：對照下面 10 項。少了哪一項、或要用到沒公開的東西，就停下來回報，不要自己去補。

`models`：

1. `Session`：建的時候給這個 Bot 的資料政策（K117 ⑦）；問的時候給用途，這次只有「Bot」。
2. 中立的請求：系統說明、訊息（你的、Bot 的、工具結果）、工具清單、思考模式、這一步最多輸出多少（`models-normalize` S1）。
3. 中立的結果：文字、思考、工具呼叫（編號、名稱、參數；參數壞了的標記和原本的字）、結束原因（五種）、用量（可以是「沒有」）、原生附件（哪一家、哪個模型）。
4. 錯誤：類別（`models-errors` S1 那張表的每一類，加上「上下文預算不夠」，K112 ⑦）、訊息代碼和參數。
5. 換模型紀錄（前、後、原因）和通知。通知這次只收下，不處理。
6. 說「是哪個模型」的型別（供應商、網址、模型名稱）和思考模式的型別：寫進「一輪開始」，也交給編譯器。
7. 能力表裡這個模型的那一筆：只轉交給編譯器，`runner` 自己不讀裡面的數字。

`context`：

8. 編譯的函式和它的輸入：這件任務的事件、這段對話的原始紀錄、記憶（這次是空的）、固定那一段的幾塊（照順序）和工具說明、這次用哪個模型和它的能力。
9. 編譯的輸出：組好的中立請求（就是第 2 項）、清單（可以存起來、有編號）、要先記下的事件（收起、少放）、這一步要留的輸出、估算。
10. 錯誤「上下文預算不夠」，帶缺多少。

`tests/harness` 的假模型要做得到：照腳本回工具呼叫（一步一個、一步好幾個）、回文字、回用量、回錯誤碼；記下收到的每個請求。做不到哪一樣也停下來回報。

## 這次的整合測試怎麼算驗到（K119 ⑰）

- 用 `runner` 的公開介面起一輪。模型是真的 HTTP 打假模型；電腦是假電腦端；紀錄是記憶體實作。
- 規格步驟寫「在〔桌面／手機〕送「…」」的＝用那個發起者起一輪，你的話是「…」。
- 前提寫「Bot 的電腦」、預期只看規則和流程的＝假電腦端（宣告成 Bot 的電腦）。
- 這一層算驗到的觀察點：
  - 「任務狀態＝」：把紀錄裡這件任務的事件交給 `domain` 的 `replay` 算。不准讀回合程式自己記在記憶體裡的狀態。
  - 「證據清單包含」：紀錄裡的證據。
  - 「模型收到的請求」：假模型記下的請求。
  - 「檔案…」：假電腦端的檔案。
  - 「這件任務的紀錄…」：紀錄裡這件任務的事件，照編號排。把關的結果（直接做、被拒絕和原因）讀「把關結果」那一筆。
- 這一層**不算**驗到的：「畫面出現」「推播送出」「按〔按鈕〕」。預期裡有這些的列，用描述性的名字，編號留在基準檔，回報列出來。

- **編號只在整列都驗到時才用**（K86）。規格寫 1,000 組就跑 1,000 組，不准縮小。

## A 段：事件、紀錄的介面、沒有模型的骨架

   - 加一筆時，事件的號由記憶體實作照加入的順序給（K113 ①：這是執行端自己的暫時順序）。事件的 ID 由執行端在產生時給。
   - 加一筆失敗 → 這一輪停下、回錯誤。不准當成寫好了繼續做。
3. **先記再做的順序**（`task-journal` S1、`turn-loop` S3）：
   - 「要做什麼」那一筆寫好了，才叫 M7c 的入口去做。
   - 「問模型」那一筆寫好了，才送請求。
   - 附一個性質測試（描述性的名字，500 組）：每個執行過的動作，紀錄裡「要做什麼」那一筆的順序早於假電腦端記下的那個操作。

## B 段：一步

一步＝問一次模型，加上它那一次要的每個工具都有了結果。照 `turn-loop` S2 的八個位置，不准調換：

| 位置 | 這次怎麼做 |
|---|---|
| ① 看停止和取消 | 沒有來源。留一個介面，這次的實作永遠回「沒有」 |
| ② 收插話 | 同上 |
| ③ 看預算 | **這次不做**。位置留好，同上 |
| ④ 套用換模型的要求 | 同上 |
| ⑤ 組上下文 | 第 4 項 |
| ⑥ 問模型 | 第 5 項 |
| ⑦ 記下回答 | 第 6 項 |
| ⑧ 一個一個做動作 | 第 7 項。每個動作開始之前還有一個看預算的位置，一樣只留位置 |

4. **組上下文**（`context-build` S1、S5，`turn-loop` S4）：
   - 每次問之前叫一次編譯器。材料從紀錄讀：這件任務的事件、這段對話的原始紀錄。記憶這次傳空的清單。
   - 固定那一段這次給三塊，照 `context-fixed` S1 的先後：身分（Bot 的名字和指示；只放時區）、這台電腦是哪一種和它的規則、工具說明。AnyBot 自己寫的字用 `turn-` 開頭的訊息代碼，照使用者的語言排；還沒設定用英文。
   - 編譯器說「要記下的事件」→ 先寫進紀錄，再送請求。
   - 清單存進「存原文」，「組了上下文」只帶它的編號、用哪個模型、估算。
   - 編譯器回「上下文預算不夠」→ 不送任何請求；任務＝卡住（細項「上下文預算不夠」）；這一輪結束（`context-must` S3）。
5. **問模型**：
   - 先寫「問模型」（帶第幾步），再送。
   - 編譯器給的請求原樣交給 `Session`。不准在這裡再改、再截。
   - 這一步要留的輸出由編譯器給（K112 ⑤）。
6. **記下回答**：
   - 「模型的回答」：文字、思考、每個工具要求（編號、哪個工具、參數）、結束原因；原生內容只當附件。
   - 另一筆「用量」：輸入和輸出的 token，對到哪一份清單。模型沒回用量就照實記「沒有」，不准補 0。
7. **做動作**（`turn-loop` S3、S5、S7）：
   - 照回答裡的順序，一個一個做，不同時做。
   - 每一個都走 M7c 的單一入口。`runner` 不准直接呼叫電腦介面。
   - 把關的設定在**每個動作之前**向那個介面要一次，不要一輪只讀一次（`turn-loop` S13）。這次後面是一份固定的值。
   - 每一個依序寫：把關結果 →「要做什麼」→「開始」→「完成」或「失敗」→ 證據 → 動作層的驗收結果。
   - 被拒的動作只有把關結果和一筆「被拒」的證據，沒有「要做什麼」和「開始」。
   - 一個動作被拒 → 同一步排在後面的都不做，各記一筆「沒執行：前一個動作被拒絕」。失敗的不影響後面的。
   - 入口回「要問」：照還沒定的第 6 點。
   - 證據的短編號（E1、E2…）由 `runner` 照產生的順序給，從 1 開始、連續，交給入口。
   - 每個工具要求都要有一個結果給模型，包括被拒的、沒執行的、沒這個工具的、參數壞了的。給模型看的結果帶著那筆證據的短編號。
   - 完整的輸出交給「存原文」。

B 段做完，`make check` 全綠，commit。

## C 段：一輪

8. **開始**：
   - 收到一句話：這個 Bot 沒有一輪在跑 → 寫「任務建立」（誰開的＝你，目標＝那句話）。這次不做插話、不做排隊：已經有一輪在跑時回錯誤。
   - 寫「一輪開始」：第幾輪、發起者（你，附哪台裝置）、在哪台、用哪個模型和思考模式。之後這一輪只有「換了模型」的事件能改模型。
9. **這一輪什麼時候停**（`turn-loop` S10）。這次做這幾種，每種對到「一輪結束」的一個原因：
   - 回答沒有工具要求 → 收尾（D 段）。「要不要提醒」（`chat-followthrough`）這次永遠是不用。
   - 一定要放的放不下 → 不送請求；任務＝卡住（上下文預算不夠）。
   - 模型失敗，閘道交出失敗 → 這一步沒有任何動作被執行；任務＝失敗（出錯：類別的代碼）（`turn-loop` S11）。
   - 空白的回覆：照還沒定的第 4 點。
   - 表裡其他的原因（停止、取消、卡片、預算、模型連不到、當機、50,000 步）這次沒有來源，**不要做一半**：原因的代碼可以先定，不准有走不到的程式。
10. **模型說的話不改任何狀態**（`task-events` S6）：回覆裡寫「完成了」「已寄出」「證據：…」，只會變成一筆回答的紀錄。

C 段做完，`make check` 全綠，commit。

## D 段：收尾、閘門、報告、整條路

11. **收尾的順序**（`turn-loop` S9）：最後的回答寫進紀錄 → 寬鬆核對（這次沒有，留位置）→ 任務層驗收（照還沒定的第 3 點，這次沒有標準）→ 寫「一輪結束」（帶原因、回覆有沒有寫進紀錄）→ 狀態由事件算 → 該出報告就出。自己接下一輪（`goal-next`）這次不做。
    - 這一輪做過動作，只是最後一個回答沒有字 → 回答寫「（沒有回應內容）」的代碼，照常收尾。
12. **完成閘門**（`domain`）：
    - 狀態由 `domain` 從事件算。`runner` 不准自己決定任務是不是完成。
    - 只有對話、沒有任何動作 → 完成（已回覆）。
    - 有動作、沒有明確的標準 → 每個寫入都要通過它的動作層驗收；指令照 `task-done-gate` S6：
      - 結束碼不是 0 的動作是失敗。
      - 看最後一個不是只看的動作：它失敗 → 未驗收（驗收沒通過）；它成功 → 較早的失敗不算。
13. **交付報告**（`trust` 的純函式，`report-delivery`）：
    - 輸入：這件任務的事件、證據、最後那則回覆。**同樣的輸入得到位元組一樣的報告**。不看時鐘。
    - 什麼時候出（S1）：有動作的任務到了完成、未驗收、失敗 → 出一次，寫成一筆紀錄。只有對話的不出。「做到哪」那一種是預算的事，這次不做。
    - 內容（S2 的一部分）：目標、結果（主狀態和細項）、摘要、「要你注意」、步驟清單、每一步連到的證據、動作層驗收的結果、每個判斷的來源（規則／程式檢查／模型判斷）。
    - 摘要就是最後那則回覆，原樣放，不多問模型一次。沒有完整的最後回覆 → 摘要處放「摘要沒有產生」的代碼（S6）。
    - 「要你注意」這次只放一種：失敗的動作（S4 最後一點）。
    - **這次不做**：逐句分級（S3）、四級各幾句、其他固定標記、「需要你決定的事」。這些是 M7h。
14. **整條路**就是 `T-turn-loop-2`，這是這次最重要的一個測試。另外把所有事件重播一次，得到一樣的狀態。
15. 另外用描述性的名字測：
    - 假模型回「完成了。證據：已送出 3 則」→ 證據清單沒有任何送出，狀態不受影響。
    - 改檔之後重讀的雜湊不相符 → 不是完成。
    - 閘道失敗 → 任務＝失敗，沒有任何工具被執行。
    - 一步 3 個工具，中間那個被一律拒絕的規則擋下 → 第三個沒有執行，結果是「沒執行：前一個動作被拒絕」；模型的下一個請求有 3 個結果。
    - 入口回「要問」的動作（例如 Bot 的電腦上 `git push`）→ 沒有執行，沒有自動允許。
    - 最後一個不是只看的動作失敗（`make` 結束碼 2）→ 未驗收（驗收沒通過）。這是 `T-task-done-gate-8` 的內容；那一列還要「沒有推播」，這一層驗不到。
    - 上下文預算不夠 → 假模型沒有收到任何請求；任務＝卡住。
    - 固定那一段的三塊照順序出現；使用者語言設成繁體中文和沒設定時，各是那個語言排出來的字。

D 段做完，`git merge dev`，`make check` 全綠，commit。

## 規則（請照做）

- **模型的字不會改變狀態**。從模型的輸出到任務事件只有兩條路：一筆回答的紀錄、工具要求。工具要求一定經過信任層。
- **每個對外動作都過把關**。`runner` 不直接呼叫電腦介面，不自己建通行證。
- **先記再做**。「要做什麼」「問模型」寫好了才動手。
- **狀態只由事件算**。`runner` 不另外存一份「現在是什麼狀態」當真相；要知道狀態就重算。
- **預算這次不碰**：不檢查、不寫預算用量和超過預算的事件、不加「步數」這個項目、不改 `domain` 裡算預算的函式、不做一輪 50,000 步的保險。兩個看預算的位置留好就好。測試都不設任何上限。
- **帶規格編號的測試，要證明它擋得住**：
  - 每一個帶編號的測試寫好之後，把它守的那條規則在產品程式裡故意改壞（一次改一處，不 commit），跑那個測試，確認變紅，再改回來。
  - 回報列一張表：測試、改壞了什麼、有沒有變紅。
  - 改壞了還是綠的測試，不准帶編號：先把測試補到會紅。
  - 例子：`T-turn-loop-3` 把「被拒的動作不寫要做什麼」改成照寫；`T-turn-loop-9` 讓給模型看的結束碼不從實際結果來；`T-turn-loop-11` 讓只有對話的任務也出報告；`T-task-done-gate-7` 把「較早的失敗不算」拿掉；`T-files-edit-7` 讓出現 2 次時照樣改第一個。
- **預期的值不准呼叫被測的產品函式來算**：
  - 雜湊在測試裡另外算，或寫死已知的值。
  - 該不該被拒、是成功還是失敗，由產生器在產生腳本時就記下。
  - 任務該是什麼狀態，由測試照規格寫出來，或由產生器在造資料時就定好。讀「任務狀態＝」用 `replay` 是觀察的方法，不是算答案的方法。
  - 不准「先跑一次產品拿結果，再拿同一段程式的結果去比」。
- **不准默默退回**：紀錄寫不進去、清單存不進去、模型沒回用量、工具的參數不對、編譯器回錯誤，都照實回錯誤或照規格停下。不准用 `unwrap_or`、`unwrap_or_default`、把錯誤丟掉的 `.ok()`。
- **不准為了測試加東西**：`runner` 不准有測試用的旗標、建構函式、`cfg(test)` 的另一條路。假的東西從建構函式傳進去。
- **被測的要是產品真正在用的那個迴圈**，不是測試裡另外寫一份簡化版。
- **時間走 `Clock`**，測試用假時鐘。要推假時鐘的測試：在同一個工作裡用一個迴圈，「做完了就離開；不然真的等 10 毫秒、把假時鐘往前推、再看一次」，整個迴圈有 10 秒的真實期限。不要另外開一個工作去推時鐘，不要用通知。
- **測試啟動的東西要收掉**：假模型的伺服器、背景的工作，都要有「離開範圍就一定停掉」的保護（測試中途失敗也一樣）。回報前用 `ps` 確認沒有留下任何程序。
- **名稱帶編號＝驗完那一列全部的預期**。
- 這次沒有的功能（卡片、停止、插話、換模型、記憶、預算）**不要順手做一半**。留一個介面、一個永遠回「沒有」的實作就好。
- 規格沒寫清楚的，不要猜，寫進回報的「要問的問題」。不得不先做時，選最小、之後好改的做法，也寫進回報。
- **40 分鐘內要有一個全綠的 commit**。做不到就先停下來回報做到哪。
- **同一個測試跑到第 3 次還不過，就換做法；換了還不行就跳過，寫進回報。**
- 不准改寫歷史、不准 push、不要用 `gh`、不准用 `pkill` 或 `killall`。暫存檔放自己工作區的 `target/`。不改 `spec/`。
