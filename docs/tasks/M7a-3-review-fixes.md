# M7a-3 審核修正

M7a-2 的修正和 M7a-3 我看過了。上一輪的三個問題都改對了：送出層是真的可以換的一層、建不出客戶端會回錯誤、產品程式不能自己發通行證。信任憑證的核心邏輯也是對的：內容一模一樣才走特例，照樣檢查名稱和期限，握手的簽章交給函式庫驗，沒有接受任何憑證的路。

還有下面幾項，改完就可以合。

## 1. 不准多信任一份內建的根憑證

`crates/foundation/src/certs.rs` 的 `TrustStore::new`，除了作業系統的信任清單，還加了 `webpki_roots::TLS_SERVER_ROOTS`（函式庫內建的一份根憑證）。

規格（`settings-n9` S2、`spec/09` K115）是：**只相信作業系統信任的，加上使用者加進清單的**。內建那一份不在裡面：公司的電腦把某個根憑證拿掉了，我們不能自己又把它信任回來。

- 拿掉內建的那一份，連同用不到的相依套件。
- 作業系統的信任清單**完全讀不到**時：回錯誤，往上報，不准默默當成空的、也不准換成別的清單。讀到一部分、有幾張壞掉的：用讀得到的，壞掉幾張記在回傳的結果裡給呼叫的人。
- 能用作業系統自己的驗證方式（例如它會查的撤銷、公司裝的根憑證）就用；做不到寫進回報。
- 伺服器映像裡有沒有系統的信任清單是 REL-1 的事（已經在補），這裡不用管。

## 2. 憑證錯誤的種類，不准用訊息的文字判斷

- `certs.rs` 的 `fault_from_text`：用 `err.to_string()` 裡有沒有「NotValidForName」「Expired」這些字來分類。
- `certs_check.rs` 的 `map_webpki`：用訊息裡有沒有「not valid for name」「expired」來分類。

函式庫改一個措辭，分類就錯了，而且不會有任何測試發現。改成比對錯誤的種類（列舉值）。不認得的種類歸到「其他」，並保留原本的錯誤。

每一種各附一個測試：不被信任、名稱或位址不對、還沒生效、過期。

## 3. `cfg!(test)` 也要擋

iron-laws 的新檢查擋了 `cfg(not(test))` 和掛錯地方的 `#[cfg(test)]`。再補上：產品程式裡不准用 `cfg!(test)`（在一般程式碼裡判斷是不是測試編譯）。附「塞進去會被擋」的測試。

## 4. `Makefile` 的測試目標先不要動

你把 `_test-body` 改成記下 nextest 的結束碼、最後 `exit` 它。你抓到的問題是真的（測試失敗時整行還是成功），而且很重要，謝謝。但這個改法讓同一行的另一半失效了：紀錄裡出現「ignoring unknown configuration keys」時不會再失敗。

- 另一個 agent 正在做完整的修正（`docs/tasks/HOTFIX-make-test.md`），會直接進 `dev`。
- 你這邊：`Makefile` 的 `_test-body` 改回跟 `dev` 一樣。之後合 `dev` 時，`Makefile` 的衝突一律用 `dev` 的版本。
- 在那個修正進來之前，你每次 `make check` 之後自己多看一眼 `target/nextest.log` 最後的總結，確認是全部通過。
