# WIKI-1：寫給人看的 GitHub wiki

使用者要一份 wiki，原話是：「要詳細寫我的流程、設計理念、安裝、架構，等任何我需要知道的，給人看的，不可以寫太難，要圖文並茂」。

原稿放在 repo 的 `docs/wiki/`，一頁一個 Markdown 檔。監督者審過之後，會把這個資料夾發佈到 GitHub wiki。你不用發佈，也不能 push。

你在並行工作（`AGENTS.md` 第七節）：自己的工作區和分支。這次**只寫文件**，不改程式、不改 `spec/`。

## 讀者是誰

- 第一次接觸這個專案的人：使用者本人，和之後想參與的人。
- 會用電腦，但**不一定會寫程式**。
- 只有「開發流程」「專案結構」「分支與發佈」這三頁，可以假設讀者會基本的 git 和命令列。

## 內容從哪來

只能寫 repo 裡查得到的東西：

- `spec/`：最重要的是 `04`（產品核心）、`02`（架構）、`06`（技術選型）、`07`（資料夾結構）、`09`（決定，以它為準，K93–K111 是最新的方向）、`10-behavior/`（行為）。
- `docs/plan.md`（里程碑）、`docs/testing.md`、`AGENTS.md`、`README.md`、`Makefile`、`.config/nextest.toml`。
- 實際的程式和 git 紀錄：用來確認「做到哪了」。

規則：

- 規格沒寫的不要猜，也不要寫舊版 AnyBot 的事。
- **不准把還沒做的寫成已經做好。**每個功能都標狀態：✅ 已經做好、🚧 正在做、📝 規劃中。狀態要對照 `docs/plan.md` 和實際的程式。現在大部分產品功能還是 📝，App 只有空殼，照實寫。
- 不放個人資料、本機路徑、IP、金鑰、信箱。

## 怎麼寫

1. **不可以寫太難。**
   - 用白話和短句。一句話講一件事。
   - 專有名詞第一次出現時，用一句話解釋，並連到 `名詞表`。
   - 先講「這對你有什麼意義」，再講它怎麼做到。
   - 多用例子。例如講任務流程時，用「你說『幫我整理這份報告』」一路講到完成。
2. **每頁開頭三行以內**，說完這一頁在講什麼、適合誰讀。
3. **圖文並茂。**
   - 每個主要概念配一張圖或一張表。圖的上面或下面有一句話，說明這張圖在講什麼。
   - 圖用 Mermaid（GitHub wiki 會直接畫出來），寫在 ```` ```mermaid ```` 區塊裡。
   - 只用 GitHub 支援的圖型：`flowchart`、`sequenceDiagram`、`stateDiagram-v2`、`gitGraph`。
   - 節點上的字用雙引號包起來，避免語法錯誤。一張圖大約 15 個節點以內，太大就拆成兩張。
   - 至少要有這些圖：整體架構、資料流、一輪的流程、把關到驗收、任務狀態怎麼變、記憶怎麼進來和升級、上下文怎麼組、換模型、分支流程、檢查和發佈的流程、開發流程。
   - 比較、清單、狀態用表格。
4. **語言**：繁體中文、台灣用語，不要夾簡體字。程式名稱、指令、檔名保留英文。
5. **頁面之間的連結**用 GitHub wiki 的寫法：`[[頁面名稱]]`，或 `[[顯示的字|頁面名稱]]`。連到 repo 裡的檔案（例如規格）用完整網址 `https://github.com/igs170911/AnyBot/blob/main/…`。
6. **每頁最後有一節「想看細節」**，列出這一頁根據的規格檔案和段落、決定編號。

## 做完自己檢查

- 每個 `[[…]]` 連結指到的頁面都存在。
- 每個 Mermaid 區塊的第一行是上面四種圖型之一，括號和引號都有成對。
- 每個標 ✅ 的功能，在程式裡真的找得到；找不到就改成 🚧 或 📝。
- 從頭到尾讀一遍，把難懂的句子改短、改白話，把簡體字改掉。
- `make check-fast` 全綠（`docs/` 可以寫中文，但還是要確認沒有弄壞別的）。
