# M7b 審核修正：中途修正

你在 `t_context_mask_2` 上卡住了：同一個測試在 30 分鐘裡改了又跑六次，每次 3–6 分鐘，還在 `.config/nextest.toml` 給 `t_context_` 的測試加了 90 秒 × 4 次的寬限。我先停下這一輪。工作區裡還沒 commit 的改動都在，沒有被動過。

## 方向

1. **把 `.config/nextest.toml` 改回去。** 不准為了一個慢的測試放寬逾時。逾時是用來抓卡住的測試的（`AGENTS.md` 第三節）。
2. **這個套件的每個測試，在平常的測試編譯下要在 30 秒內跑完。** 這是純函式的套件；一個測試要好幾分鐘，代表每一組做了太多事，不是逾時太短。整個 `make check` 也會被拖慢，所有工作區都在排隊等同一把測試鎖。
3. **讓每一組變便宜，不是減少組數。** 規格那一列要 1,000 組，照樣 1,000 組。做法（你挑，先量再改）：
   - 先量時間花在哪：一組有幾步、每一步組一次要多久。每一步都從頭組一次、步數又多，總共是步數的平方。
   - 可以放的大小（可讀長度）選小一點，例如 4,000–20,000 token；這樣十幾步就會觸發收起，不需要上百步。規格那一列沒有寫可讀長度的範圍，你選的範圍要能讓「收起」「15% 的門檻」「600 字以下不收」「最近 2 步」每一種都真的發生，並在測試裡數一下每種各發生了幾組（至少要有一定的比例，寫成斷言）。
   - 結果的長度用幾種固定的大小混著產生（短的、剛好 600、幾千字），不要每一組都產生很長的字串。
   - 只有在量過之後，確定是編譯器本身在除錯模式下太慢，才可以讓這個套件在測試編譯時開最佳化（在根目錄的 `Cargo.toml` 為這一個套件設 `opt-level`），而且要在回報裡寫出改之前、改之後各花多久。
4. **同一個測試已經跑了六次。** 照規則，第 3 次不過就該換做法。這次照上面的方向改；改完還是超過 30 秒或還是不過，就停下這一個，用描述性的名字留著已經驗到的部分、編號放回基準檔，寫進回報，先做別的。
