## 一、Windows：規則檢查工具不在 Windows 上跑

失敗的是 `tools/iron-laws` 的 `test_iron_laws_real_repo_clippy_tomls_match_their_packages`：在 Windows 上找不到任何檔案（很可能是路徑分隔符號）。`tools/` 底下是專案自己的規則檢查程式，只在 Linux 的完整檢查裡跑，不是產品。

- Windows 的單元測試範圍只放產品的套件（`crates/`、`apps/`）。`tools/` 底下的套件放進「編了但不跑測試」或「不編」的清單（你判斷哪一個；寫原因）。不要為了 Windows 去改這些工具的路徑處理。
- 清單和實際對得上的那道檢查，現在只認 `test-harness = …` 那一種寫法（`windows_lists.rs`）。點號的寫法、子表、只在某個平台的區段、間接依賴（經過 `testenv`、`live-model`）都漏掉。改成從 `cargo metadata` 的相依關係算，不要讀文字。

## 二、開發版那條路

1. **發佈到一半失敗，頁面會壞掉。** `publish-release.sh` 用 `--clobber` 上傳：同名的舊檔會先被刪掉、再上傳新的。開發版的安裝檔和 `SHA256SUMS` 每次都同名，所以上傳到一半失敗時，頁面上是缺檔或新舊混在一起，說明還寫著舊的 commit。另外 `:dev` 映像在頁面那一步之前就推了：頁面那一步失敗時，映像是新的、頁面和標籤是舊的。
   - 要做到：任何時刻，看得到的開發版頁面要嘛是**完整的舊版**、要嘛是**完整的新版**，不會混。做法你定（例如先把新的完整建成另一個草稿，全部上傳成功後再換過去、刪舊的），但要查 GitHub 的官方文件確認每一步的行為，寫進回報。
   - 映像和頁面要對得上同一個 commit：`:dev` 在頁面換成功之後才移；頁面那一步失敗，`:dev` 不動。
2. **「一定要是 `dev` 最新的 commit」只在一開頭的 `guard` 查。** 只重跑舊的那次的 `publish`、或兩次開發版的建置先後顛倒時，舊的 commit 會最後發佈。在排隊進入發佈的那個工作裡、真正動手之前，再查一次。
3. **開發版和正式版的發佈共用同一個排隊位置**（`release.yml` 的 `concurrency`）。照 GitHub 文件，新排進來的會把正在等的那一個取消：正式版在等的時候，下一次開發版一排進來，正式版就被取消了。兩個管道分開排隊（下面第 5 項修完之後，兩邊不共用任何名字）。查官方文件確認寫法。
4. **`guard.sh` 挑錯檢查結果**：它拿 `main` 上第一個 check suite，不管是哪個工作流程的（例如 Wiki 那次）。改成只看 CI 那個工作流程在 `main` 上、對這個 commit 的那一次；而且 Linux、Windows、macOS 三個工作都要成功（K111：要全綠），不是只看 Linux 的 `check`。
5. **開發版和正式版還共用名字**：12 位 commit 的標籤、兩個架構的 commit 標籤。`ws → dev → main` 是快轉，同一個 commit 兩個管道都會發，那個標籤就指到後發的那一個。改成每個管道有自己的名字（例如開發版加 `dev-` 開頭），兩邊不共用任何一個標籤。
6. **`move-latest.sh` 讀不到目前的 `latest` 時當成「還沒有」**，就不檢查順序直接移。改成：只有映像倉庫明確回「這個標籤不存在」才算第一次；其他任何錯誤（網路、登入、格式）都停下來報錯，不移。版本格式只收 `數字.數字.數字`，不收四段、空的、前面補 0 的。
7. **映像的索引加註解要 OCI 格式。** 審查沒辦法確認推上去的是 OCI 還是 Docker 格式；照 Docker 文件，是 Docker 格式的話，加註解那一步第一次真的發佈時就會失敗。查文件確認，必要時明確設定成 OCI。`latest` 加註解之後是新的索引，摘要跟發佈頁上寫的不會一樣：發佈頁寫的摘要要寫清楚是哪一個（各架構的，或版本那個標籤的），`release-notes.md` 跟著改。

## 三、自我測試（`release-selftest.sh`）

1. **`latest` 的那幾個「拒絕」的情境沒有 `docker` 的替身，只看結束碼是 1。** `vdev` 那個情境，把格式檢查整段刪掉也會過（順序檢查也會擋它）。更嚴重的是：順序檢查壞掉時，腳本會呼叫**真的** `docker` 去改 `:latest`；CI 上因為沒登入所以失敗、結束碼 1、測試照樣綠；在一台登入了 ghcr 的電腦上跑 `make check`，就會真的動到 `latest`。
   - 每一個情境都要有 `docker`、`gh`、`git` 的替身，**而且替身是唯一找得到的那一個**（`PATH` 裡沒有真的）。替身被叫到的時候記下參數。
   - 每個拒絕的情境要驗「被哪一條規則擋下」（看錯誤訊息或替身的紀錄），不是只看結束碼；而且驗「替身沒有收到任何會改東西的指令」。
2. **`guard` 的測試繞過了真的查詢**：用環境變數換掉了查 check suite、查「在不在 `main` 上」、查 `dev` 最新 commit 這三件事，所以「怎麼挑檢查結果」從來沒被測到。「`main` 失敗、`dev` 成功」那個情境設的是 guard 根本不讀的值。改成用 `gh` 的替身回不同的 API 結果，讓 guard 走真的那段程式。
3. 「候選版的版本字串有 commit」那個情境一定成立，因為放進去的值本來就有 commit。改成會失敗的寫法。
4. 每個情境都證明會失敗：把它守的那條規則改壞、看到變紅、再改回來。回報裡列成表。

## 四、其他

1. `ci.yml`（Linux、Windows、macOS 三個工作）和 `security.yml`：會跑 `pnpm install`、cargo 建置腳本的工作，取出程式碼時 `persist-credentials: false`。第 6 輪只改了 `release.yml`。
2. 注入清單（`workflows.rs`）還漏：完整的 ref（`github.ref`、`github.head_ref`）、用中括號取同樣的欄位、整個事件轉成 JSON、GitHub 文件列為不可信的欄位（issue 和 review 的內容、commit 訊息、commit 作者的名字和信箱、PR 的 head label）。照 GitHub 的安全強化文件補齊，寫出你參考的是哪一份。
3. `docs/release.md`：第 24–25 行還寫舊的「先刪頁面再建、先移標籤」；第 60 行教人用重跑舊 commit 的方式退回 `:dev`，現在 guard 會拒絕。照現在的做法改。
4. `ci.yml` 裡 pnpm 的安裝用 `sudo` 跑，暫存資料夾變成寫在 `target/` 裡；快取是空的時候，那個資料夾會變成 root 的，之後 `make check` 寫不進去。不用 `sudo`，或裝完把擁有者改回來。
5. `wiki.yml`：從工作分支手動執行時，工作會被跳過，但工作流程層的 `concurrency` 照樣會把 `main` 正在跑的發佈取消。把 `concurrency` 放到工作那一層，或群組帶上 ref。
6. `docs/testing.md` 第 18 行左右「共用編譯輸出」那一段已經過時：不同路徑的工作區共用一份 `target-dir` 時，cargo 把每個執行檔放在同一個固定位置，一個工作區會跑到另一個工作區編的執行檔。現在每個工作區各自一份；工作區上一層的 `.cargo/config.toml` 只設 `incremental = false` 和 `debug = "line-tables-only"`（為了省磁碟）。照這個改寫那一段，並寫出原因。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。同時有別的 agent 在別的工作區做事，編譯和測試會互相等，屬於正常。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`（測試裡的替身除外）、不准用 `pkill` 或 `killall`。不准在這台電腦上跑真的 Docker。遇到「Operation not permitted」是沙箱在擋，不要繞過。
