# REL-1 審核修正（第 6 輪）

第六次預演：**發佈那一半全部通過**（四個桌面安裝檔、兩個伺服器映像）；三種系統的檢查裡，Linux 過（470 個 Rust 測試，`linux tests ran: 479`）、macOS 過（464 個，`macos tests ran: 473`）、Windows 的「compile the product」過了，「basic tests」失敗。紀錄在 `target/ci-logs/rel6-ci-failed.log`。

另外，合併之前我請了一個獨立的審查把整個發佈流程讀過一遍。它確認預演、手動執行、PR（包括從 fork 來的）都不會發佈任何東西。但它找到一批問題，大部分在「正式發佈」那條路上：那條路預演從來不會跑到，所以六次預演都沒看到。下面每一項我都對過程式。

先做：`git merge dev`。

## 一、Windows 的基本測試編不過

```
error[E0433]: cannot find `unix` in `os`
error[E0599]: no method named `signal` found for reference `&ExitStatus`
error: could not compile `test-harness` (lib)
```

原因：`apps/server`、`crates/models`、`crates/server` 的測試相依（dev-dependencies）有測試工具。跑這些套件的單元測試時，cargo 一定會編測試工具，不管有沒有 `--exclude`。

1. Windows 上跑單元測試的範圍改成：測試相依裡沒有測試工具的產品套件。上面三個套件在 Windows 上**照樣編譯**（compile 那一步不變），只是不跑它們的測試。
2. 「不編的」和「編了但不跑測試的」是兩份清單，都寫在 `docs/testing.md`，各自寫原因。工作流程照清單，不要散在指令裡。
3. 加一道本機就擋得到的檢查：清單和實際對得上。產品套件的測試相依有測試工具、卻不在「不跑測試」的清單裡 → 擋下來；清單裡的套件其實沒有那個相依 → 也擋下來（清單不能只增不減）。
4. `windows tests ran:` 的數字照新的範圍更新到回報裡。

## 二、正式發佈那條路（一定要修）

1. **移動 `latest` 的工作一定會失敗。** `release.yml` 的 `latest` 工作沒有取出程式碼，`deploy/release/move-latest.sh` 不存在。補上；取出的是那個 Release 的標籤指到的 commit。
2. **`latest` 不檢查格式和順序。** `move-latest.sh` 只擋有 `-` 的。
   - 標籤要完全符合 `v數字.數字.數字`，否則拒絕（現在 `vdev` 會把 `latest` 指到開發版的映像）。
   - 只准往前：要移過去的版本比現在 `latest` 指的版本舊，就拒絕並說原因。現在 `latest` 指的是哪個版本，要從映像倉庫查得到（例如映像上的版本標記），不要靠猜。
3. **候選版的映像被標成正式的版本號。** `push-images.sh` 在 stable 管道一律用 `Cargo.toml` 的版本當標籤，所以 `v0.1.0-rc.1` 會推成 `:0.1.0`。改成：候選版的映像標 `:0.1.0-rc.1`；只有 `v0.1.0` 才標 `:0.1.0`。`guard.sh` 交出來的值要分得出這兩種。
4. **開發版和正式版共用 `arch-amd64`、`arch-arm64` 兩個標籤**，再用這兩個名字組成多架構的映像；兩邊的 `concurrency` 群組又不一樣。兩個發佈重疊時，正式版的某個架構可能是開發版的映像。改成用每個架構推上去之後拿到的**摘要**來組，不經過會被別人改掉的名字。
5. **開發版發佈到一半會被取消，而且是先刪頁面再建。** `ci.yml` 的 `concurrency` 會取消同一個分支上還在跑的那一次，包括已經開始發佈的；`publish-release.sh` 先刪掉開發版頁面再重建。結果：連推兩次、第二次檢查失敗 → 開發版頁面不見，或頁面和映像不是同一個 commit。
   - 已經開始發佈的那一次不准被取消（檢查可以被取消，發佈不行）。
   - 不要先刪再建：新的安裝檔都上傳成功之後，才換掉舊的。任何一步失敗，舊的開發版要原封不動。
   - 頁面上寫明這是哪個 commit；映像和頁面要對得上同一個 commit。
6. **打了標籤的 commit，版本字串裡沒有 commit。** `git describe --tags --always` 在剛好有標籤的 commit 上只印標籤名。正式版的版本字串因此只有重複的標籤名。改成一定帶 commit（規格 `install-n10`）。映像那個「版本字串對不對」的檢查現在兩邊用同一段邏輯，所以抓不到；預期值要另外算。
7. **安裝檔的檔名有空白**（`AnyBot Dev_0.1.0_x64-setup.exe`）。GitHub 會把 Release 附件檔名裡的空白換掉，`SHA256SUMS` 裡寫的檔名就對不上，文件裡教的驗證指令會失敗。先查 GitHub 的官方文件確認它怎麼換；然後在算雜湊**之前**把檔名改成沒有空白的，`SHA256SUMS`、`docs/release.md`、wiki 都用改過的名字。
8. **`guard.sh` 查「檢查有沒有綠」的方式不可靠。** 它拿那個 commit 上第一個叫 `check` 的結果。同一個 commit 通常有好幾個（推 `dev` 一次、推 `main` 一次）：可能拿到還在跑的、可能拿到別的分支的。規則是：算數的是 **`main` 自己那一次**對這個 commit 的檢查，而且已經結束、結果是成功。還在跑 → 拒絕並說「還沒跑完」；別的分支的綠不算。
9. **開發版模式不看分支。** `guard.sh` 只要收到 `mode=dev` 就發佈。重跑一次舊的執行，會把舊的 commit 重新發佈成開發版。加上：呼叫的那一次必須是 `dev` 分支，而且那個 commit 就是 `dev` 現在的最新一個，否則拒絕。

## 三、wiki

`wiki.yml` 的手動執行沒有限定分支：從工作分支手動跑，會用那個分支的 `docs/wiki` 蓋掉整個 wiki、刪掉其他頁。手動執行也只准在 `main`。

## 四、關卡的洞

1. `tools/iron-laws` 的工作流程檢查：
   - 認不出 `permissions: write-all` 這種寫法。要擋。
   - 「不准把別人給的字放進指令」的清單少了：分支或標籤的名字、Release 的標籤名、手動執行和被呼叫時的輸入。補上。
   - `.github/workflows` 這個資料夾不存在時會通過。要改成失敗。
2. 「會啟動 PostgreSQL 的測試一定要叫 `pg_*.rs`」那道檢查，只掃最上層的測試檔、只找一種寫法，比 `docs/testing.md` 說的少。讓兩邊一致：要嘛檢查做到文件說的，要嘛文件照實寫它擋得到什麼、擋不到什麼。
3. `tools/test-count.sh`：有給網頁測試的紀錄檔路徑、但檔案不存在時，現在當成 0。要失敗。
4. 從快取拿回來的工具（`ci.yml` 裝工具那一段）沒有再驗雜湊。拿回來之後也要驗。
5. `pnpm` 是用 npm 裝的，沒有驗雜湊。查官方文件，用有驗證的裝法（例如 `packageManager` 欄位帶雜湊），五個用到的地方都要改。

## 五、小的

1. `release.yml` 交出一個沒有人設定的映像摘要；`deploy/release/release-notes.md` 叫使用者去比對一個沒有公布在任何地方的摘要。二之 4 做完之後摘要就有了：把它真的交出來、寫進發佈頁；做不到就把那兩處拿掉。
2. `images/server/Dockerfile` 的使用者用數字，不要用名字。
3. 建映像用的 BuildKit 映像沒有釘版本。釘住。
4. 會跑相依套件建置腳本的工作，取出程式碼時不要留著憑證（`persist-credentials: false`）。

## 六、正式發佈那條路要有不靠真的發佈也能驗的測試

二的每一項都是「讀程式才看得出來」的。這條路第一次真的跑，就是使用者第一次打版本標籤的時候，不能到那時候才知道。

- `deploy/release/*.sh` 的每一個判斷（模式、標籤格式、候選版和正式版的映像標籤、`latest` 的格式和順序、開發版只准 `dev` 的最新 commit、檢查結果怎麼挑）都要有測試：給它一組假的環境變數和假的查詢結果，看它交出什麼、拒絕什麼。會打 GitHub、會推映像的那幾個指令，測試時換成印出「本來會做什麼」的替身。
- 這些測試接進 `make check`。
- 至少包含這幾個情境：候選版標籤、正式版標籤、標籤不在 `main` 上、`main` 的檢查還在跑、`main` 的檢查失敗而 `dev` 的成功、`vdev`、比 `latest` 舊的版本、重跑舊的開發版執行。

## 驗證和回報

- 每一大項做完 `make check` 全綠就 commit 一次，不要全部做完才 commit。
- 發佈的條件只准變得更嚴，不准放寬。預演（推 `ws/rel-*`、手動執行）照樣不能建 Release、推映像、動標籤、改 wiki。
- 回報（簡短）：每一項怎麼改的；哪幾項你查了官方文件、查到什麼；Windows 的兩份清單和新的測試數；六的測試各驗了哪些情境；有沒有哪一項你認為不該照做、為什麼。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。同時有別的 agent 在別的工作區做事，編譯和測試會互相等，屬於正常。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`、不准用 `pkill` 或 `killall`。不准在這台電腦上跑 Docker。遇到「Operation not permitted」是沙箱在擋，不要繞過。
