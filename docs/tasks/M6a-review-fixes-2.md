# M6a 審核修正（第 2 輪）

M6a 是伺服器的地基：資料庫和遷移、伺服器設定、啟動、註冊、登入、改密碼、邀請碼、次數限制。分支 `ws/m6a`。

到目前為止：第一次交件後，獨立審查找到四個安全問題和十幾個沒驗到整列的測試；第一輪修正（`docs/tasks/M6a-review-fixes.md`、`docs/tasks/M6a-review-fixes-midcourse.md`）做完後，我推上 GitHub 驗、又請獨立審查對了一次。結果：

- GitHub 的 Linux 檢查：523 個測試全過，但 `make check` 停在 `sqlx-check`（見第五節）。
- 審查：第一輪的安全項目大部分修對了（關伺服器的入口拿掉了、紀錄裡沒有秘密、不存在和被停用的帳號、來源位址、第一個註冊的是管理員、暗號用固定時間比對）。但有兩個新的阻擋項，而且**上一輪回報說「補齊」的測試，有八個實際上沒有補**。

這一輪換人接手。前一位做的東西不要整個重寫：先讀懂，照下面的清單改。下面每一項的檔名和行號是審查當時（`3e794bf`）的位置，我對過前兩項和抽查了幾個測試；其餘的你動手前自己再對一次規格那一列和現在的程式，發現清單寫錯就照實回報。

先讀：`AGENTS.md`；`spec/09` 的 K108、K113、K116；`spec/10-behavior/5-devices-account.md` 的 `account-login`、`account-n10`、`account-bind`、`server-invite`、`server-boot`、`server-n1`、`server-n2`、`server-n8`、`server-n14`、`install-n22`；`spec/10-behavior/2-trust.md` 的 `safety-n10`、`safety-n11`。然後 `git merge dev`。

## 一、阻擋項

1. **登入的次數限制可以用大小寫繞過。** `crates/server/src/api_account.rs` 的登入入口把**還沒正規化**的帳號名稱交給次數限制，正規化在後面才做。`bob`、`Bob`、`bOb` 各有各的計數，驗的卻是同一個帳號：名字有 n 個字母，同一個位址在一個時間窗裡就能猜 2^n × 8 次。照 K116 ④：名稱在入口正規化一次，之後每個地方（次數、查帳號、`Idempotency-Key` 的範圍、紀錄）都只拿正規化過的。註冊、改密碼、管理動作一起檢查。命令列的重設密碼（`cli_reset.rs`）沒有正規化，長度還是照位元組算的，一起改。
   - 測試：同一個帳號用不同大小寫輪流猜，總次數不能超過上限。
2. **遷移檔會刪東西。** `migrations/server/0002_scopes.sql` 拿掉 `idempotency` 的主鍵、換一個新的，還加了一個沒有預設值的必填欄位（表裡有資料時會失敗；舊版的伺服器也寫不進去了）。規則是遷移只加不刪。這兩個遷移檔都還沒進 `dev`、沒有任何資料庫用過：把 0002 併進 0001，讓 0001 一次建成最後的樣子。之後加一道檢查：遷移檔裡出現 `DROP`（包括 `DROP CONSTRAINT`、`DROP COLUMN`、`DROP INDEX`）、改欄位型別、沒有預設值的必填新欄位 → 擋下來。

## 二、安全和行為（應該修）

1. **整個帳號的上限（40 次）沒有排隊。** 鎖是照「位址＋帳號」上的，不同位址的請求在預設的隔離等級下看不到彼此還沒提交的那一次：計數到 39 時，最多還有 7 個會過。`t_safety_n10_2` 斷言剛好 40，只是剛好時間對上才過。每個位址的上限和註冊的上限是對的（先上鎖、寫入後才數、被擋就退回）。帳號的上限照同一個做法。改密碼的上限現在是先看再記、沒有鎖（`api_ops.rs`），一起改。
   - 測試：真的同時從很多個不同位址送，通過的剛好等於上限。不能靠時間剛好。
2. **註冊。**
   - 兩個人同時用同一個名字註冊，輸的那個現在拿到 201「建立了」（衝突被默默吃掉）。要回帳號名稱已經有人用的錯誤。
   - 邀請碼是在算雜湊之前、那筆交易外面檢查的：邀請碼換掉之後，舊的碼還能成功一次。檢查要在同一筆交易裡。
3. **登入被停用的帳號回 403，API 文件寫 401。** 以 K116 ③ 為準，改文件和產生出來的客戶端。
4. **`apps/server/src/server_run.rs` 用了只有 Unix 才有的訊號，沒有分系統。** 產品的套件在 Windows 上也要編得過（發佈流程會在 Windows 上編全部的產品套件）。分系統處理，Windows 上用它自己的結束方式。
5. **還在默默吃掉錯誤的地方**：`cleanup.rs`、`caller.rs`、`pass_hash.rs`、`server_run.rs`、`problems.rs`。另外 `rows.rs` 用錯誤訊息的文字判斷錯誤種類，改成照錯誤的種類或代碼。
6. 沒人用的程式：`tests/app-test/src/startup.rs`、`note_startup_logs`。拿掉。

## 三、測試啟動的程序還是沒收乾淨

我在完整的 `make check` 跑完之後，看到一個 PostgreSQL 還活著（`target/tests/testenv/data` 那一個，最後瀏覽器測試那一步啟動的）。上一輪的回報寫「沒有殘留」。

- 原因（審查讀出來的，動手前你自己確認）：`tests/testenv/src/main.rs` 的停止寫在 `serve` 後面，而 `serve` 不會回來；程式沒有處理訊號。瀏覽器測試收尾時（`tests/e2e/src/env.ts`）送 SIGTERM 就走、不等它結束；程式當場結束，收尾的程式一行都沒跑，資料庫是獨立的背景程序所以留下來。
- 現在所有的保護都靠解構（`Drop`）：只管得到測試失敗和提早回傳，管不到 nextest 逾時砍掉、Ctrl-C、被訊號結束。
- 要做到：
  1. `testenv` 收到結束的訊號要把自己啟動的東西停掉再走；收尾的那一端要等它真的結束（有期限）。
  2. 測試工具啟動時，先掃 `target/tests` 底下留下來的 pid 檔：那個程序還在、而且確實是這個工作區的測試程序，就先停掉。只能照 pid 檔裡的 PID，不准照名稱。
  3. `tools/sqlx_prepare.sh` 的兩個等待沒有期限，加上。
- **「程序不會留下來」的自我測試現在不可能失敗**（`tests/harness/tests/harness_self.rs`：它拿只有 PID 的輸出去找指令的文字）。改成真的會失敗的；加一個 PostgreSQL 的情境、一個「被訊號結束」的情境。
- 回報前不要只跑 `ps` 就寫沒有殘留：沙箱裡 `ps` 可能看不到東西。用 pid 檔和連線埠確認，並寫明你是怎麼確認的。

2. **每個帶編號、這一輪動到的測試，都要證明它會失敗**：把它守的那條產品規則暫時改壞（例如不檢查暗號、把上限改大、把最短密碼改成 6），看到測試變紅，再改回來。回報裡列成表：測試、改壞了什麼、有沒有變紅。
3. **為了躲檢查而寫的測試**：`startup_helpers_answer_for_a_live_server` 把每個共用的輔助函式叫一次、結果幾乎都丟掉。把那些輔助函式搬進 `app-test` 這個函式庫（共用的東西本來就該在那裡），刪掉這個測試。`public_url_server_reserves_the_port_for_the_first` 是誠實的但重複了，留一個。
4. **會因為機器忙而失敗的**：`t_safety_n10_2`、`t_account_login_4`、`t_account_login_9` 用真的時鐘量延遲（樣本各只有 3、6、19 個）；`pg_cleanup_prunes_old_records` 清理超過 50 毫秒就失敗；註冊那幾個有 2 秒的上限。這台機器同時有好幾個 agent 在編譯。量時間的改成：要比較的兩種情況穿插著量、樣本夠多、比中位數；不是在量時間的就不要有真實時間的上限（用假時鐘，或只留很寬的保險期限）。規格那一列的數字不准自己放寬；在忙的機器上真的做不到就寫進回報。
5. **`t_account_bind_1` 沒有網路時會失敗**：它對一個公開的位址開 UDP 來找這台的區網位址。改成直接列出這台的網路介面來找，不需要對外的路由。
6. **`make check-fast` 的篩選**（`.config/nextest.toml`）是照測試名字的片段：還是跑到 5 個要 PostgreSQL 的測試，又漏掉 `crates/trust`、`crates/server` 裡 7 個不需要資料庫的單元測試。規則統一成：會啟動 PostgreSQL 的測試放在檔名 `pg_` 開頭的測試檔，篩選照檔名（`binary(/^pg_/)`），不照測試名字。
7. 簡體字的檢查只有 49 個字，漏了很常見的（这、个、们、为、来、时、请、码、号、无、错、误 都不在裡面）。補到至少涵蓋常用字裡簡繁不同的那些；字表怎麼來的寫在註解旁邊的文件裡（不要從網路上抓不明來源的表，查得到出處的才用）。

## 五、GitHub 上的檢查

`make check` 在 GitHub 的機器上停在 `sqlx-check`：`error: no such command: sqlx`。這個分支新加的檢查要用 `sqlx` 的命令列工具，`.github/workflows/ci.yml` 沒有裝。照那個檔裡其他工具的規矩補上：版本釘死、跟 `Cargo.lock` 裡的 `sqlx` 同一版、下載的東西驗雜湊（沒有官方的預先編好的檔就從原始碼裝、鎖版本，並放進快取）。`iron-laws` 對工作流程檔的規則照樣要過。

## 驗證和回報

- 順序：一 → 二 → 三 → 四 → 五。每一大項 `make check` 全綠就 commit，不要累積。
- 全部做完 `git merge dev`、`make check`。
- 回報（簡短，照 `AGENTS.md` 第六節）：每一項怎麼改的；第四節「會失敗」的那張表；基準檔裡這個里程碑的編號最後還剩哪幾個；程序有沒有殘留、怎麼確認的；清單裡哪幾項你對過之後認為寫錯了；有沒有哪一項你認為不該照做、為什麼。
- 做不完的照實寫，不要寫成做完了。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。同一個測試跑到第 3 次還不過就換做法；還是不行就寫進回報、先做別的。同時有別的 agent 在別的工作區做事，編譯和測試會互相等，屬於正常。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`、不准用 `pkill` 或 `killall`（要停程序只能指定 PID）。函式庫的行為要查文件或原始碼確認（`~/.cargo/registry/src/` 可以讀），不要憑記憶寫。遇到「Operation not permitted」是沙箱在擋，不要繞過。
