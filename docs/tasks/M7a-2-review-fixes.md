## 1. 性質測試走的不是產品的那條路

現在 `Gateway::complete` 裡有一個 `take_recorded`：

- 測試編譯時（`cfg(test)`）它會攔下請求，改走 `client_recorded.rs` 裡**另外一份**回應處理。
- 正式編譯時（`cfg(not(test))`）它什麼都不做。

結果是四個性質測試沒有經過產品真正的這幾段：送出、狀態碼的判斷、串流的組合、不完整的回應、等第一個字的時間。兩份已經不一樣了：正式的那份把 3xx 歸成轉址，測試那份歸成一般的狀態碼。`T-models-egress-6` 要驗「轉址」，驗到的是測試那一份。

這也是 `AGENTS.md` 第三節不准的「只為測試存在的模式」，不是任務檔說的「從建構函式換掉的一層」。

改成：

1. 最底層做成一個介面：「送出一個請求（網址、標頭、內容），拿回狀態碼和內容；串流是一塊一塊回來」。**正式和測試都編進去**，不掛 `cfg(test)`。
2. `Gateway` 對外的建構函式用真的那一個（reqwest）。套件裡面另外有一個建構函式可以傳別的實作進去，給套件自己的測試用；這個建構函式不對外公開。
3. 這一層以上的程式，測試和正式是**同一份**：金鑰檢查、通行證、編碼、狀態碼、轉址、串流組合、不完整的回應、逾時、重試。
4. 拿掉 `take_recorded`、`client_recorded.rs`，和所有 `cfg(test)`／`cfg(not(test))` 成對的函式、欄位。
5. 性質測試用的假送出層要能表達：一塊一塊的串流、在任意位置斷掉、轉址、各種狀態碼、連不上、等太久（透過假時鐘，不真的等）。四個性質測試改用它，照樣 1,000 組。
6. iron-laws 加一道檢查，掃 `crates/` 和 `apps/` 的產品程式：
   - 不准出現 `cfg(not(test))`。
   - `#[cfg(test)]` 只准掛在 `mod` 和 `use` 上，不准掛在函式、欄位、`impl`、敘述上。
   - 附「塞進去會被擋」的測試。現有的程式有違反的，這次一起改掉；改不了的列進回報，不准加例外清單了事。

## 2. 建不出客戶端時，不准退回預設的客戶端

`client_http.rs` 的 `product_client()`：

```
.build().unwrap_or_else(|_| reqwest::Client::new())
```

預設的客戶端**會跟轉址**。建不出來的時候，「閘道固定不跟轉址」這個保證就默默不見了。

- 建不出來就是錯誤，往上回。`Gateway::new` 改成會失敗的（回 `Result`），呼叫的人在啟動時處理。
- 整個套件找一遍同樣的寫法（出錯時默默換成預設值），一起改。

## 3. 通行證不能讓呼叫的人自己挑政策

`SendPermit::for_endpoint` 是公開的，政策由呼叫的人傳進來。任何人寫一個 `DataPolicy::Cloud { .. }` 就換得到雲端的通行證；`test_support/permit.rs` 就是這樣做的。測試這樣用沒關係，但之後寫執行端的人也可以這樣繞過「這個 Bot 只送本機和區網」。

用工具擋：

- 產品程式（`crates/` 裡 `models` 以外的套件，和 `apps/`）不准呼叫 `SendPermit::for_endpoint`。加進 clippy 的 disallowed-methods，照現在擋時間函式的做法；附「塞進去會被擋」的測試。
- 訊息要寫清楚該怎麼做：問模型一律透過 `Session`，政策是建 `Session` 時給的那個 Bot 的政策。
- `crates/models` 自己、`tests/` 底下的可以用。
