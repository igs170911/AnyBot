# M5b：狀態引擎的預算照新的規則（小任務）

規格改了預算的幾條規則（`spec/09` K119 ⑧，`spec/10-behavior/1-followup.md` 的 `task-budget`）。`crates/domain` 的狀態引擎是 M5 照舊規則做的，這次把它改過來。只動純邏輯，不碰執行端。

你在並行工作（`AGENTS.md` 第七節）：自己的工作區和分支 `ws/m5b`，從 `dev` 切。

**你是一次性執行的**：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。

## 先讀

- `AGENTS.md`：五條鐵律、第三節、第六節、第七節。
- `spec/09`：K100、K104、K119（⑤、⑧、⑨）。
- `spec/10-behavior/1-followup.md`：`task-state`（S2、S3、S5）、`task-events`（S1–S3）、`task-budget`（整段，包括那張表和 9 個測試列）、`turn-loop` S1（一步、動作的定義）、`goal-brake`。
- `spec/10-behavior/README.md`：「一步、動作」那一段。
- 程式：`crates/domain` 裡算任務狀態、預算、完成閘門的那幾個檔，和它們的測試。

## 要做的

1. **到上限本身不算超過**（`task-budget` S3）。現在的引擎是用量一到上限就算卡住。改成：用量已經到上限、又要再開一個動作或再問一次模型，才算超過；剛好用完、這一輪自己結束的，照常收尾。
2. **預算多一個項目「步數」**：問這個 Bot 的模型的次數（`turn-loop` S1 的「一步」）。規格裡數工具的那一項叫「工具呼叫」，數的是開始執行的動作；被拒的、沒執行的不算。
3. **沒設定時的上限**（`task-budget` S1 的表）：步數 300、工具呼叫 600、時間 4 小時；token、花費不限。每一項都可以改，也可以改成不限。
4. **時間只算有一輪在跑的時候**：等你、排隊、卡住的時間不算。時間從事件算，不讀系統時鐘。
5. **/goal 的任務**：步數、工具呼叫、時間這三項沒設定時的上限，每一輪各算各的（新的一輪開始，拿來比的數字從 0 算起）；使用者自己設的上限是整件任務累計的；用量的數字照樣一直累計。
6. **拒絕之後換做法做完算完成**（K119 ⑤、`task-state` S3、S5）：只看最近一輪。現在的引擎是拒絕過一次，這件任務就到不了完成。
7. `protocol` 裡預算項目的型別要跟著加「步數」。事件的其他欄位這次**不要動**（另一個任務會照 `task-events` S2 整批補）。

## 規格編號

這次要整列驗到的：`T-task-budget-1`、`T-task-budget-2`、`T-task-budget-6`、`T-task-budget-9`、`T-task-state-9`。

- `T-task-budget-1`、`2` 現在已經有測試，但那兩列的預期改了（`1` 多了「剛好用完、自己結束的那幾組不是卡住」；`2` 的字從「步」改成「動作」）。把測試改到符合現在的那一列。
- `T-task-budget-3`、`4`、`5`、`T-task-effects-1`、`2` 現在有測試：對一次現在的那一列，還符合就不動；不符合就改。
- `T-task-budget-7`、`8` 是整合的列，要執行端，這次不做。
- 同一段裡其他種類是「單元」「性質」、只靠引擎就驗得到、而且現在還在基準檔裡的列：不用做，但請在回報裡列出來。

兩條這幾輪審查之後加的規則：

- **預期的值不准呼叫產品的函式來算。** 測試裡自己有一份照規格寫的答案。性質測試的產生器在造每一組的時候就決定它該是什麼結果。
- **每個帶編號的測試都要證明它會失敗**：把它守的那條規則暫時改壞（例如改回「到上限就卡住」、把 300 改成 301、讓 /goal 的上限變成整件累計），看到測試變紅，再改回來。回報裡列成表：測試、改壞了什麼、有沒有變紅。
