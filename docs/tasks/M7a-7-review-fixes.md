## 一、GitHub 上 Linux 的失敗

`t_models_egress_3` 在 Linux 上失敗（`cloud recorded 0`：主模型連續 503 之後，備用的雲端模型一次都沒收到請求）。本機是過的。紀錄在 `target/ci-logs/m7a-ci-2-failed.log`。審查猜是測試推假時鐘太快（每 20 毫秒推 2 秒），在真的連線完成之前，15 秒的連線期限就先到了；沒有確認過。先找出真正的原因，再決定改產品還是改測試。不要用放寬時間、加重試、或在 Linux 上略過的方式讓它過。

## 二、連上之後等回應沒有上限（阻擋項）

`transport.rs` 的 `open_wire`：15 秒只跟「連上」賽跑；連上之後，等回應標頭那一段沒有任何計時。https 的時候，`reqwest_wire.rs` 還跳過了先連線的那一步，所以 TCP 和 TLS 也都在沒有計時的那一段。客戶端也沒有設任何 reqwest 的逾時。等第一個字、出字後 35 秒，都要等標頭來了才開始算。

- 後果：伺服器接了連線、但一直不回標頭（或 https 的主機接了 TCP、TLS 一直不完成），這一問就永遠不回來，不重試、也不換備用。模型清單（`catalog_fetch.rs`）一樣，45 秒的上限從來沒有作用。
- 要做到：「連上」包括 TCP 和 TLS，15 秒；連上之後到第一個字，照 `models-errors` 的「等不到第一個字」計時；模型清單整個 45 秒。全部走 `Clock`。
- 測試要走真的 HTTP 那一層：假模型接了連線但一直不回 → 時間到是「等不到第一個字」（或連不上，看是哪一段），不是一直等；https 的握手一直不完成 → 15 秒後是連不上。

## 三、金鑰的目的地檢查永遠會過（阻擋項）

`client_place.rs` 的 `key_for`：清單上的網址**或**實際要連的位址，任何一個對得上就放行。清單上的網址是從端點自己的網址組出來的，永遠對得上，所以「金鑰送錯地方」那個錯誤永遠不會發生（`client.rs`、`catalog_fetch.rs`）。只檢查**實際要連的目的地**。測試：把 `api.openai.com` 固定到另一個位址 → 金鑰不送出、回金鑰目的地的錯誤。

## 四、代理照分類決定（阻擋項）

`client_http.rs` 不走代理的名單是固定的字串和網段。`[::ffff:127.0.0.1]` 照 K117 ① 是本機，卻會走代理。照新的 K117 ②：每一個網址照分類決定，本機和區網一律直接連，只有雲端的走代理。加測試：IPv6 包著 127.0.0.1、區網位址、沒有點的名字，在設了代理時都不經過代理。

## 五、編號和 Windows 的根憑證

1. `T-models-errors-4`、`T-models-errors-5`、`T-models-normalize-14` 放回 `tools/spec-trace/baseline.txt`，測試改描述性的名字。原因：errors-4「不重試的只送一次」只在第一個失敗剛好是不重試時才檢查，另一個斷言找的訊息代碼根本不會出現；errors-5 沒有交錯、沒有產生「等不到第一個字」、同一個參數只拿一次的上限放太寬、空白的結果沒檢查；normalize-14 串流還是切成固定四等份，工具呼叫的預期是拿輸出自己的結束種類比。這三個之後另外排一件補到整列。
2. Windows（`certs_os.rs`）除了根憑證，還把系統的「中繼憑證」那一區當成可信的根。那一區系統會自動放東西、一般程式也能加進去。照新的 K117 ②：只讀根憑證那一區。
