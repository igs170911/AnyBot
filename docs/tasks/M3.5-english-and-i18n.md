# 里程碑 M3.5：程式碼和測試裡不准有中文

使用者定的新規則（`spec/09` K91、K92，`AGENTS.md` 第五條鐵律）：

> 把 code 跟測試裡面寫中文的地方，全部改成英文，前端要用 i18n，後端也是可以給個代碼可以顯示，code 裡面不要有中文的輸出。

現在 repo 裡有 130 個檔案含中文：toml、Rust、yaml 最多，還有 Makefile、README、package.json。這次全部處理掉，再加上關卡，以後擋得住。

先讀：`spec/09` K91、K92；`spec/07` 新加的 `locales/` 和 `messages`；`spec/05` §2a 新加的一列；`spec/10-behavior/README.md` 開頭新加的「「」裡的中文怎麼讀」。

## 要做的

1. **翻譯檔 `locales/`。**
   - 兩種語言：`en`（基準）、`zh-TW`（必須齊全）。
   - 建議用 Project Fluent（`.ftl`）：有參數、複數；Rust 和 TypeScript 都有官方函式庫。照 `AGENTS.md` 先查維護者、最近更新、RustSec 紀錄，寫進回報。覺得別的格式更好，先停下來問。
   - 訊息代碼要穩定，照領域分組，例如 `server-startup-listening`。一個代碼只代表一個意思，不准拿舊代碼改成別的意思。
   - 規格有寫「」字句的，`zh-TW` 就用規格的字句。例如 `install-n22` S3 的啟動那一行、「無法使用連接埠 N：…」，`server-n14` S2 的「啟動檔的權限太開放」。
2. **`crates/messages`**（`spec/07`）。
   - 只做「代碼＋參數＋語言 → 字」。
   - 翻譯檔在建置時打包進程式，執行時不讀檔。
   - 沒有語言設定時用英文（K92）。伺服器的語言設定在 M6 跟著伺服器設定進資料庫。
3. **TypeScript 那邊**：放在 `web/ui` 裡。
   - 建置時讀同一份翻譯檔。
   - 語言照瀏覽器的語言，只認 `en` 和 `zh-TW`，其他用英文。使用者在設定裡改語言是 M8 的事。
4. **後端回代碼。**
   - problem+json 加上 `code`（字串）和 `params`（物件），`title` 用英文。OpenAPI 的 schema 和例子、TS 客戶端都要一起更新。
   - 執行事件裡給人看的錯誤（現在的 `RunError { message }`）改成代碼加參數，AsyncAPI 也要更新。
5. **全部改英文。**
   - **使用者看得到的**（命令列和伺服器印的字、錯誤訊息、畫面上的字）改成代碼，字放進翻譯檔。
   - **給開發者看的**直接改成英文，不進翻譯檔。包括：
     - 檢查工具的輸出（iron-laws、depcheck、spec-trace、api-docs）。
     - `clippy.toml` 的原因、redocly 規則的訊息、`plugin.js`。
     - 斷言訊息、Makefile、CI 設定。
     - `Cargo.toml` 和 `package.json` 的說明。
     - `tauri.conf.json`、`capabilities` 這類設定。
   - **README 全部改英文**：repo 要開源，英文是慣例。中文說明要留的話，搬進 `docs/`。
   - **API 文件**：utoipa 的摘要和說明、AsyncAPI 的標題和說明都改英文，重新產生 yaml、HTML、TS 客戶端。
   - `tools/spec-trace/baseline.txt` 的說明行改英文。規格編號不動。
6. **測試。**
   - 不准有中文。
   - 比對代碼和參數，不比對字面。
   - 規格要「輸出某一句」的（例如 `T-install-n22-1`），執行檔現在沒有語言設定，所以印英文。測試拿 `messages` 用 `en` 排出那個代碼的字，跟執行檔的輸出比。
   - 測試資料需要中日韓文字時，用 Unicode 跳脫寫法，例如 `"\u{4f60}\u{597d}"`。
7. **關卡**（每一道都附「塞進去會被擋」的測試）：
   - **中日韓文字**：所有被 git 追蹤的檔案，除了 `locales/`、`spec/`、`docs/`、`AGENTS.md`，出現就擋。
     - 字元範圍要寫清楚：中日韓統一表意文字（含擴充）、中日韓符號和標點、全形字元、平假名、片假名、韓文。
     - 產生出來的檔案不例外：它們的來源已經是英文了。
   - **翻譯檔一致**：
     - `en` 和 `zh-TW` 的代碼一樣。
     - 同一個代碼的參數一樣。
     - 程式用到的代碼都存在。
     - 沒有人用的代碼要刪。
     - 建議從 `en` 的翻譯檔產生 Rust 的列舉和 TS 的型別。這樣代碼打錯就編譯不過，產生的檔案也要有「重新產生不一致就擋」的關卡。
   - 這些關卡都接進 `make check` 和 `make check-fast`。

## 不要做

- 改產品行為。這次只換字和換做法，原本的測試、規格覆蓋數字（5 個）都要維持。
- 動 `spec/`、`docs/`（`docs/testing.md` 那類新檔可以英文或中文，`docs/` 不受這條規則管）、`AGENTS.md`。
- 動 git 歷史裡舊 commit 的訊息。

修完 `make check` 全綠再 commit 一次（不准改寫歷史），照 `AGENTS.md` 第六節用繁體中文回報。另外附上：
- 選了哪個翻譯格式和函式庫、它們的維護狀況。
- 翻譯檔總共幾個代碼。
- 掃中文的關卡排除了哪些路徑。
