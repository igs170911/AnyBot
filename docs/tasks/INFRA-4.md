# INFRA-4：雲端檢查的編譯快取，工作分支也存（小的）

完整的 `make check` 改成在 GitHub 上跑（agent 用雲端檢查把自己的 `ws/*` 分支推上去）。同一個分支在一輪裡常常會推好幾次，所以 GitHub 上那一次要快。

現在（`.github/workflows/ci.yml` 的 `check` 工作）：

- 編譯輸出（`target`）的快取**只在 `main` 存**。GitHub 的快取照分支分開，別的分支只讀得到自己的和預設分支（`main`）的。`main` 要等使用者核准 PR 才會往前，所以快取很舊，工作分支每次都要重編很多。
- 2026-11-26 量到的：`check` 工作 10–18 分鐘，其中 `make check` 那一步 6–13 分鐘。
- 這個 repo 的快取已經用了 11.3 GB（上限 10 GB，超過會照「最久沒用」刪掉），每個分支各存一份 cargo 下載、npm 之類的小快取。

你在工作區 `~/Documents/AnyBotNext-wt/infra2`，分支 `ws/infra-2`。

## 要做到

1. **工作分支和 `dev` 也存編譯輸出的快取**：同一個分支第二次推上去，讀到的是自己上一次存的；第一次推讀 `main` 的。編譯完就存，不要等測試全過（一輪裡常常是測試沒過、改一下再推）。
2. **控制大小**：存之前清掉不需要的（例如這一次的測試執行檔以外、`target` 裡跟這次無關的大東西，你量過再決定），把一份編譯輸出快取的大小寫進回報。小的快取（cargo 下載、pnpm、playwright……）能共用就共用，不要每個分支各存一份。
3. `build-windows`、`build-macos`（REL-3 之後每個工作分支都會跑）也照同樣的方式存編譯輸出。
4. 照實寫進 `docs/testing.md`（或 CI 的說明文件）：哪些快取存在哪、分支刪掉之後快取怎麼辦（監督者刪分支時會一起刪它的快取）。
5. 不准為了快拿掉任何檢查步驟、不准改 `make check` 檢查的內容。
6. 順手修（M6b-1 審核發現的）：`ci.yml` 算遷移檢查的比對基準時有 `|| echo HEAD` 的退路；找不到 merge-base 時檢查會悄悄變成什麼都不比。改成找不到就失敗，說原因。

## 驗證和回報

這一件改的是 `.github/`，雲端檢查會擋（CI 設定由監督者推）；本機跑一次完整的 `make check`。commit，訊息開頭 `INFRA-4：`。`git merge dev`。回報：改了什麼、一份快取多大、你預期第二次推上去的 `make check` 那一步會快多少。我會推兩次量實際的時間。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准自己 push、不要用 `gh`、不准用 `pkill` 或 `killall`。遇到「Operation not permitted」是沙箱在擋，不要繞過。
