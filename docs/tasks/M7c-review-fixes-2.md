# M7c 審核修正（第 2 輪）

第 1 輪修得很紮實：複查抽查了 8 種繞法（換行接指令、`sudo -u root`、`cd x && git push`、`git -C r push`、`nohup npm publish`、`rm a.txt /etc/passwd`、`rm $HOME/x`、連到外面的捷徑）都擋住了；「要問」的單子欄位不公開、不能複製、用掉就沒了、被拒的動作拿不到單子，也都對。

複查又往下挖了一層，找到幾個洞。這一輪我把結構定下來，讓這一類洞從設計上就不會發生，不用一個一個補。行號是 `ws/m7c` 現在的位置，動手前再對一次。

先做：`git merge dev`。另外 GitHub 的 Linux 檢查是紅的（見四之 1）。

## 一、結構：電腦只接受寫死了完整操作的單據（阻擋項）

現在的問題（都是同一個根源：通行證和真正要做的操作是分開的兩樣東西）：

- 每次成功執行，通行證都放在回傳結果的公開欄位裡（`pipeline_run.rs`）。拿到它的程式可以直接對電腦再做一次（例如重跑已經核准過的 `git push`），沒有把關、沒有證據。
- 通行證的鑰匙沒有包含寫入的內容，所以寫入或修改的通行證可以寫任何內容。
- 指令的鑰匙被轉成小寫、換行被折成空白，所以 `echo ok reboot` 的通行證也能跑 `echo ok⏎reboot`。
- 鑰匙沒有標是哪一種操作；假電腦端從通行證本身拿操作的種類。所以「指令 `write:/etc/passwd`」的通行證可以拿去寫 `/etc/passwd`。
- 「每一個操作先查通行證」只寫在文件裡；電腦的介面（trait）任何套件都能實作，以後真的電腦端可以默默跳過。

改成這樣：

1. **單據就是操作本身。** 把關放行之後，`trust` 做出一張單據，裡面寫死完整的操作：哪一種（讀、寫、修改、指令、查路徑…）、哪台電腦、所有參數原樣（路徑、寫入的內容、要換掉的舊字串和新字串、完整的指令原文，不轉大小寫、不整理）。
2. **電腦的每一個操作只收這張單據**，沒有另外的路徑、內容、指令參數。電腦照單據上寫的做，所以沒有東西可以對不上，也沒有東西可以忘記檢查。
3. 單據只有 `trust` 建得出來（欄位不公開、沒有公開的建構方式、不能複製、不能序列化回來），呼叫的時候整張交出去（用掉就沒了）。
4. **任何回傳給呼叫者的東西裡都沒有單據或通行證**：結果只有把關紀錄、證據、給模型看的結果、一行摘要。
5. 單據上寫的電腦跟實際被呼叫的電腦對不上 → 拒絕。
6. `tools/iron-laws` 的通行證守護、`crates/computers/README.md`、`tools/iron-laws/README.md` 照新的結構改寫，寫對它擋得到什麼。

## 二、其他兩個阻擋項

1. **「要問」的單子沒綁電腦**（`pipeline.rs`）：回答時傳哪台電腦就在哪台跑。在 Bot 的電腦上，`sudo git push origin` 會問（Bot 的電腦允許 `sudo`）；使用者核准後，呼叫者拿你自己的 Mac 回答，`sudo` 就在一台本來一律拒絕它的電腦上跑了，證據卻寫第一台。單子裡記下發單時的電腦（名稱和宣告的能力）；回答時電腦不一樣 → 拒絕。
2. **一律允許、這段對話都允許、掛鉤的結果，是呼叫者自己傳的布林值**（`gate_flow.rs`、`gate_full.rs`）。設成真，任何不是底線的拒絕都會變成放行。`trust` 要自己從規則清單和這個動作算出來；呼叫者只能傳規則清單本身（使用者和管理員設的那幾條），不能傳「算好的結果」。

## 三、看穿包裝和拆指令（阻擋項）

1. 現在只拿掉一次普通的外包裝、再拿掉一次 `sudo`。在 Bot 的電腦上，`sudo nohup mkfs.ext4 /dev/sda1`、`sudo env reboot`、`sudo FOO=1 shutdown -h now` 都直接跑了，`sudo nohup git push` 也沒有問。改成反覆拿掉，直到最前面不是包裝為止：`sudo`、`doas`、`env`（連同 `名稱=值`）、`nohup`、`nice`、`timeout`、`stdbuf`、`xargs`、`command`、`exec`，各自帶值的選項一起跳過。
2. 這些寫法也要看穿：`sh -c '…'`、`bash -c '…'`（拆裡面那段）；`$(…)`、反引號、`(…)` 子殼（拆裡面那段）；`if/then/else/fi`、`while/until/do/done`、`case/esac` 這些關鍵字當成分隔；指令名被引號包住（`'reboot'`）去掉引號；絕對路徑（`/sbin/reboot`）看最後一段的名字。
3. **還是看不懂的，一律「要問」**，在每一台電腦都一樣：`eval`、引號沒配對、把 here-doc 餵給 shell、看穿之後還是看不出第一個字是什麼。寫進規則的原因代碼。
4. **刪除的目標**（`command_target.rs`）：現在只從「開頭就是刪除工具」的那一段收目標，所以 `rm a.txt; sudo rm -r /opt/app`、`cd /tmp && rm -rf build` 被當成自己資料夾的刪除。改成每一段都先看穿包裝再判斷；同一串指令裡前面有 `cd` 的，後面的相對路徑照 `cd` 之後的位置算，`cd` 的目標解析不了或在工作資料夾外面 → 不算自己的資料夾。
5. `git` 的全域選項：寫成 `--git-dir=.git` 這種帶 `=` 的、或不在清單上的選項（例如 `-P`）時，掃描就停了，`git --git-dir=.git push`、`git -P push` 沒被當成發佈。改成照 git 的規則跳過所有全域選項（以 `-` 開頭的都是，帶值的那幾個多跳一個），再看子指令。

## 四、測試

1. **GitHub 的 Linux 檢查是紅的**：`clone_ask_ticket_outside_trust.rs` 那個編不過的測試，macOS 和 Linux 印出來的錯誤訊息不一樣（macOS 多引了一段 Rust 標準函式庫的原始碼），比對失敗。把每個編不過的範例寫成兩個系統印出來都一樣（例如不要經過 `Option` 去叫 `clone`）。紀錄在 `target/ci-logs/m7c-ci-2-failed.log`。
2. **8 個編不過的測試裡有 2 個證明不了什麼**：`clone_pass_outside_trust` 失敗的原因是缺 trait 和方法不存在（就算通行證可以複製也照樣失敗）；`edit_gate_verdict_outside_trust` 叫的函式根本不存在。`build_gate_verdict`、`build_ask_ticket` 除了要擋的那個錯，還夾了別的錯。每一個範例都要只有**一個**錯，而且就是要擋的那一個；寫法上，把它要擋的那一條規則拿掉，這個範例就要能編過（用這個方式證明，列進回報）。
3. 建證據的最後一步（`pipeline_run.rs` 的 `finish`）是公開的，任何證據都收。不公開。
4. 一到三的每一項加測試（描述性的名字），並證明會失敗。

## 驗證和回報

- 順序：四之 1（先讓 Linux 綠）→ 一 → 二 → 三 → 四的其他項。每一節 `make check` 全綠就 commit。
- 全部做完 `git merge dev`、`make check`，簡短回報：每一項怎麼改的；「會失敗」的表；編不過的測試逐一說明「拿掉哪一條規則就會編過」。
- 其他想到的寫在回報裡，不要做。

你是一次性執行的：回合一結束，背景工作就會被收掉。`make check` 用前景跑、timeout 設長（30 分鐘）。同一個測試跑到第 3 次還不過就換做法。只在自己的工作區做，暫存檔放工作區的 `target/`，不改 `spec/`。不准改寫歷史、不准 push、不要用 `gh`、不准用 `pkill` 或 `killall`。遇到「Operation not permitted」是沙箱在擋，不要繞過。
